# Прежняя раскладка (x = столбец, y = строка от метки 0) была ЗЕРКАЛЬНОЙ:
# 0->6 задавалось как +X, а 0->42 как +Y, хотя физически это направления
# «вправо» и «вниз» одного и того же вида сверху. Никакой поворот такую пару
# не совмещает с реальностью — отсюда путаница x/y и рывки в разные стороны.
#
# ПОВОРОТ МЕТОК: rot_z = -1.5708 (-90°), а не 0. Координаты центров верны,
# но сами метки лежат на поле повёрнутыми на 90° вправо (по часовой стрелке
# при взгляде сверху) — замерено на площадке 2026-08-02.
#
# Почему это нельзя оставить нулём, хотя «метка же квадратная». Квадрат при
# повороте на 90° накрывает сам себя, поэтому метка не пропадает и не
# искажается — сдвигается только нумерация её углов, а её детектор берёт из
# битового узора. Для solvePnP это значит, что наблюдаемый угол №0
# сопоставляется с модельным углом №1, и поза камеры выходит развёрнутой на
# 90° вокруг центра метки. Пока в кадре одна метка — врёт в основном курс;
# как только меток несколько, единой позы, объясняющей их все, не существует
# вовсе (каждая требует поворота вокруг СВОЕГО центра), и оценка начинает
# скакать при каждой смене набора меток в кадре.
#
# Глобальным поворотом осей карты это не лечится: центры меток остались на
# своих местах, повёрнуты только сами метки. Правится только этой колонкой.
#
