# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Код для инженерного соревнования «Энергоэстафета» (Архипелаг 2026): два БВС
(дрона) Skyris Technic 6S (PX4 + Orange Pi 5 Pro, **ROS 1/rospy, не ROS 2**)
автономно взаимодействуют с двумя зарядными станциями и доставляют груз.
Полное описание задания и регламент — `docs/TASK.md`; план работ по
приоритетам — `docs/PLAN.md`. Обе страницы на русском — пиши комментарии/
докстринги/сообщения в коде на русском, чтобы соответствовать существующему
стилю.

**Язык общения**: все ответы пользователю в этом репозитории — исключительно
на русском языке (не только код/комментарии, но и сам текст ответов Claude
Code).

Никакого ROS 1, реального дрона или `rospy` в среде разработки нет и не
будет — весь код спроектирован так, чтобы работать и тестироваться без них
(см. «Архитектура» ниже).

## Структура репозитория

В корне — только то, что запускают напрямую (`uav1_flight.py` на дроне,
`debug_axes.py`/`debug_camera.py` для отладки без моторов) и этот README; общие модули — в `lib/`, карта поля — в `config/`,
регламент/план — в `docs/`. `CLAUDE.md` — по конвенции Claude Code остаётся в
корне (иначе не подхватывается автоматически), даже несмотря на то что это не
«файл запуска» — исключение из общего правила.

Корневые скрипты сами добавляют `lib/` в `sys.path`
(`sys.path.insert(0, str(Path(__file__).resolve().parent / "lib"))` в самом
начале файла, до импорта модулей из `lib/`) — благодаря этому модули внутри
`lib/` импортируют друг друга обычными `import marker_nav as nav` без
относительных импортов и без установки пакета, и при этом каждый из них
всё равно можно запускать напрямую как `python3 lib/marker_nav.py
--self-test` (сработает, потому что соседние модули лежат в той же папке).
**Новый файл в `lib/` не нуждается в собственном sys.path-хаке** — это
делают только корневые скрипты.

**В этой ветке — только БВС-1.** Всё остальное удалено (и осталось в ветке
`main`, вернуть можно `git checkout main -- <файл>`):

- прежние полётные скрипты на глобальной локализации `aruco_map`
  (`bvs1_flight.py`, `bvs2_flight.py`, `diagnosis.py`, `lib/flight_core.py`,
  `lib/flight_nav.py`, `lib/flight_test_support.py`) — **не воскрешай этот
  подход и не тяни из него код**: полёт теперь строится только на том, что
  видно камерой (см. «Архитектура»);
- зарядная станция (`charging_station.py`, `lib/energy_relay_vision.py`,
  `lib/station_protocol.py`), захват груза БВС-2 (`lib/gripper_control.py`) и
  синхронизация двух бортов (`lib/mission_sync.py`).

Не добавляй сюда код для БВС-2 или станции без явной просьбы.

## Команды

Нет build/lint-тулинга и pytest — каждый модуль сам себе тест через
`--self-test`/прямой запуск. Это основной способ проверить, что код не
сломан, без ROS 1 и дрона:

```bash
python3 lib/marker_nav.py --self-test
python3 lib/led_interface.py --self-test
python3 debug_axes.py --self-test      # логика диагноза осей
python3 debug_camera.py --self-test    # разбор кадра и сравнение с платформой
```

`lib/marker_nav.py` без флага (`python3 lib/marker_nav.py --map ...`) печатает
деревья и маршрут для заданной раскладки — быстрый способ проверить обход
препятствий, не запуская ничего на дроне. Сам `uav1_flight.py` самотеста не
имеет: он весь про ROS, и проверяется на дроне через `--probe` (без моторов).

Самотест `marker_nav` не требует ни ROS, ни OpenCV: `cv2` нужен только
`MarkerDetector`, то есть распознаванию меток на дроне. Держи это разделение
при правках — иначе расчётная часть перестанет проверяться на десктопе.

Запуск полётного сценария на дроне и параметры CLI (`--map`,
`--start-marker`, `--station-marker`, `--station-height`, `--tree-markers`,
`--marker-size` и т.д.) — см. README.md, раздел «БВС-1 по видимым меткам»,
там же таблица «что делать, если» по каждому сообщению об ошибке и порядок
переноса кода на Orange Pi.

## Архитектура

**Принцип, общий для всех модулей**: рабочая логика не импортирует `rospy`/
`technic`/`mavros_msgs`/`cv_bridge` на верхнем уровне. Импорт ROS-специфики
спрятан внутри «backend»/«init»-функций (`uav1_flight.init_ros`,
`led_interface.use_technic_ros1_backend`) и вызывается один раз в `main()`
каждого скрипта; `cv2` точно так же спрятан в `marker_nav.MarkerDetector`.
Вся остальная логика получает нужные операции как явно переданные
callable/прокси (см. `RosLink` в `uav1_flight.py`) — поэтому её можно
прогнать в `--self-test` с обычными функциями-заглушками на десктопе без
ROS. **При добавлении новой ROS-зависимости следуй этому же паттерну**,
иначе модуль перестанет тестироваться без дрона.

Слои (снизу вверх):

1. **Инфраструктурные примитивы** (`lib/`) — не знают про конкретную миссию:
   - `lib/marker_nav.py` — вся расчётная часть полёта по меткам, без ROS:
     разбор карты (`read_field_map`/`marker_xy`), геозона (`Geofence`),
     деревья (`tree_positions`/`segment_is_clear`/`tree_hit`), маршрут по
     решётке BFS в обход деревьев (`plan_route`), зрение
     (`MarkerDetector` — `cv2.aruco`, `{ID: Marker(x, y, side, angle)}`),
     высота по стороне метки (`alt_by_side`/`hold_alt`), поворот поля в
     кадре по паре меток (`frame_yaw_from_pairs`), перевод осей
     (`field_to_body`/`body_to_field`/`frame_vector`), место дрона
     (`estimate_position`) и урезание перелёта до предела с сохранением
     направления (`limit_move`). **Ключевое: никакой телеметрии** — ни
     `get_telemetry`, ни `aruco_map`, ни TF; всё считается по кадру.
   - `lib/led_interface.py` — `set_led(pattern, color)` через
     `LEDController`/`LEDBackend`; есть `ConsoleBackend` и `CallbackBackend`
     для тестов/симуляции помимо `TechnicROS1Backend`. К полётному сценарию
     пока не подключён — индикация по Табл.1 ставится следующим шагом.

2. **Полётный сценарий** (корень репозитория) — собирает слой 1:
   - **Два режима навигации.** По умолчанию `--nav-mode aruco-map`: место
     берётся из `get_telemetry(frame_id='aruco_map')`, цель задаётся абсолютной
     точкой карты. Запасной `--nav-mode markers` — место считается по кадру
     камеры (`marker_nav`), команды идут смещением в `body`. Общее у обоих:
     взлёт, маршрут по решётке, геозона, деревья, посадка на куб.
   - **Потеря позиции — штатная ситуация, а не отказ**: телеметрия в кадре
     карты отдаёт NaN уже после 0.5 с без распознавания (документация Clover).
     `Pilot.search_lost` ищет по возрастанию риска: ждём на месте → поднимаемся
     до `climb_max` → обходим зону крестом с возвратом в точку потери. Крест
     важен именно возвратом: дрон не уползает оттуда, где он заведомо был
     внутри разрешённой зоны.
   - **На земле карты не видно** — дрон стоит на стартовой метке и закрывает
     её. Это норма: предполётная сверка не обязательна, обязательна сверка
     после взлёта.
   - `uav1_flight.py` — `MissionConfig` + `Pilot` + `run_mission`: маршрут в
     обход деревьев печатается до взлёта → вертикальный взлёт на `--alt`
     (`auto_arm=True`) → `settle()` и калибровка (эталон высоты `side_ref`,
     замер шага решётки, сверка расчётного места с координатами
     `--start-marker`) →
     `goto()` по каждому узлу маршрута → `goto(станция, blind=True)`
     (метка станции закрыта кубом, наводимся по карте от соседних видимых) →
     спуск по `/rangefinder/range` шагами и `arming(False)`. Любая ошибка
     (`FlightAborted`, выход за геозону, дерево, отказы `navigate`) гасит
     движение и сажает дрон — миссия не продолжается вслепую.
   - **`Pilot.fly(forward, left, up)` — единственное место, откуда уходит
     `navigate()`**, и устроено оно **один в один как `fly()` в `fly_head.py`**:
     все координаты уходят одной командой, `yaw=0.0` («не менять курс»),
     `frame_id='body'`, пауза `hypot(distance, up) / speed + hop_pad`.
     Поправка высоты едет той же командой, отдельной команды на неё нет.
     Правишь движение — правь там, не в обход. Курс дрона не удерживается:
     камера смотрит вниз, а поворот поля меряется по кадру заново.
   - **Прошивка экспериментальная — её не перепрошиваем.** Нельзя закладываться
     на то, что все сервисы есть: отсюда запасной путь в `Pilot.disarm` —
     если `mavros/cmd/arming` недоступен, моторы глушатся через `land()`.
   - **Закрытые метки** (`blind_markers`, по умолчанию 0, 5, 37, 48): их
     физически перекрывают площадка «Н», кубы станций и груз, камера их не
     увидит никогда. Поэтому нигде нельзя писать проверку вида «под дроном
     должна быть метка N»: над такой меткой встают счётом по карте от
     соседей, а сверка после взлёта идёт по координатам
     (`start_tolerance`), а не по идентификатору видимой метки.
   - **Место определяется по паре меток**: по одной поворот поля не измерить.
     `Pilot.yaw_ref` — `None`, пока пары не было ни разу; в этом состоянии
     `Sight.position` тоже `None`, и дрон не летит, а поднимается осмотреться.
     Не подставляй сюда ноль «чтобы работало»: это разворачивает всю карту на
     неизвестный угол (ловилось на модели как промах 1.4 м после взлёта).
   - **Два разных зазора до деревьев, не путать**: `tree_clearance` (0.5 м) —
     для планирования маршрута, `tree_guard_clearance` (0.3 м) — для сторожа.
     Сторож обязан быть мягче планировщика, иначе он запрещает ровно тот
     маршрут, который планировщик и построил, и сажает дрон посреди
     исправного полёта (воспроизводилось на модели при равных значениях).
     Соотношение проверяется перед взлётом в `run_mission`.
   - `--probe` — режим без моторов: печатает видимые метки, место, шаг
     решётки и маршрут. Это основной способ проверить зрение на площадке.

   Позиции меток читаются из `config/field_map.txt` (формат `aruco_pose`:
   `id size x y z rot_z rot_y rot_x`, нумерация построчно от левого верхнего
   угла поля 7×7) — id меток, высота станции и группы меток вокруг деревьев
   передаются как аргументы CLI, а не хардкодятся, потому что раскладка поля
   объявляется организаторами перед каждой попыткой.

   Подход перенесён из проверенного в полёте `fly_head.py` (репозиторий
   Bl1tz2200/Snake). Подробности и таблица «что делать, если» — в README,
   раздел «БВС-1 по видимым меткам».

## Важные допущения, требующие проверки на площадке

Отмечены в README.md/docs/TASK.md как непроверенные без реального ROS
1/дрона — если меняешь код рядом с ними, не удаляй эти пометки, пока
допущение не подтверждено:

- Направление нумерации `config/field_map.txt` соответствует физическому
  полю — **подтверждено** на площадке (метка 0 — верхний левый угол).
- Словарь ArUco поля — `DICT_4X4_50` (`--aruco-dict`); проверяется первым же
  `uav1_flight.py --probe`.
- Сторона метки `--marker-size` (0.33 м) — по ней считается вся геометрия
  (масштаб кадра и высота); `--probe` печатает замеренный шаг решётки для
  сверки.
- Имя сервиса армирования `mavros/cmd/arming` — стандартное для MAVROS, но
  не подтверждено явно документацией Skyris (используется в
  `uav1_flight.init_ros`, нужно только для дизарма на кубе).
- `--touchdown-range`/`--descent-step` — начальные значения, требуют
  калибровки по факту на кубе 80 см.
- `--tree-clearance` (0.5 м) — радиус крон организаторами не назван, а зазор
  по умолчанию пускает дрон вплотную вдоль ствола (маршрут короче на два
  перегона). Запас держится высотой: `--alt` 2.0 м против дерева 1 м.
  Осторожный вариант — `0.8`.
- `--hop-pad` (0.8 с) — пауза на успокоение, перенесена с другого дрона.
- Сам сценарий целиком на реальном дроне ещё не летал: проверен самотестом
  расчётной части и прогоном на модели (телепорт-симуляция, в репозиторий не
  входит).
