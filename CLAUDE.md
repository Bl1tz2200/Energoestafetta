# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Код для инженерного соревнования «Энергоэстафета» (Архипелаг 2026): два БВС
(дрона) Skyris Technic 6S (PX4 + Orange Pi 5 Pro, **ROS 1/rospy, не ROS 2**)
автономно взаимодействуют с двумя зарядными станциями и доставляют груз.
Полное описание задания и регламент — `docs/TASK.md`; план работ по
приоритетам — `docs/PLAN.md`. Обе страницы на русском — пиши комментарии/
докстринги/сообщения в коде на русском, чтобы соответствовать существующему
стилю.

**Язык общения**: все ответы пользователю в этом репозитории — исключительно
на русском языке (не только код/комментарии, но и сам текст ответов Claude
Code).

Никакого ROS 1, реального дрона или `rospy` в среде разработки нет и не
будет. **Python в этой среде тоже нет** — только заглушка Microsoft Store,
поэтому ни синтаксис проверить, ни что-либо запустить локально нельзя. Это не
временное неудобство, а условие задачи: код проверяется на борту.

## Структура репозитория

```text
uav1_flight.py         единственный полётный скрипт (~560 строк)
config/field_map.txt   карта поля 7x7 в формате aruco_pose
docs/TASK.md           задание и регламент
docs/PLAN.md           план работ (устарел в части связи со станцией)
README.md  CLAUDE.md
```

**`lib/` больше нет, и заводить его обратно не надо.** Плоский однофайловый
скрипт — это решение, а не недоделка: предыдущая версия с модулями, слоями,
классами и самотестами занимала 1472 строки и не летала ни разу. Полетел
плоский скрипт на 220 строк. Не разбивай `uav1_flight.py` на модули, не
восстанавливай `sys.path`-хак и не создавай `lib/` без явной просьбы.

**В этой ветке — только БВС-1.** Остальное удалено (и осталось в других
ветках, вернуть можно `git checkout <ветка> -- <файл>`):

- полётные скрипты на локализации по кадру камеры (`lib/marker_nav.py`,
  прежний `uav1_flight.py`, `simple_flight.py`, `debug_axes.py`,
  `debug_camera.py`) — **не воскрешай этот подход**: навигация теперь только
  по `aruco_map`;
- пробные скрипты `fly_to_station.py`, `fly_to_id.py`, `fly_to_point.py`,
  `fly_to_visible_marker.py` — их роль полностью покрыта `uav1_flight.py`;
- индикация через `lib/led_interface.py` — лента управляется напрямую
  сервисом `led/set_effect`;
- зарядная станция (`charging_station.py`, `lib/station_link.py`,
  `lib/energy_relay_vision.py`) — ветка `charging-station`; захват груза
  БВС-2 (`lib/gripper_control.py`) и синхронный взлёт (`lib/mission_sync.py`)
  — ветка `main`.

Не добавляй сюда код для БВС-2 или станции без явной просьбы.

## Команды

Ни pytest, ни линтеров, ни `--self-test` в репозитории нет — самотесты ушли
вместе с `lib/`. Единственная проверка, не требующая дрона:

```bash
python3 uav1_flight.py --check                       # карта, сводка, моторы не трогаются
python3 uav1_flight.py --check --station 192.168.0.21  # то же плюс связь со станцией
```

Она работает без ROS, потому что `import rospy` стоит ниже разбора
аргументов. **В этой среде её всё равно не прогнать** (Python — заглушка), так
что первая настоящая проверка кода — на борту:

```bash
scp uav1_flight.py orangepi@10.42.0.1:~
ssh orangepi@10.42.0.1 "python3 -m py_compile uav1_flight.py; python3 uav1_flight.py --check"
```

Не пиши в отчётах, что код проверен, если делал только правки вслепую —
скажи прямо, что проверка возможна лишь на дроне.

## Архитектура

### Отменённый принцип

Прежнее правило — «рабочая логика не импортирует `rospy` на верхнем уровне,
ROS приходит через backend/`RosLink`/`init_ros`, всё проверяется `--self-test`
на десктопе» — **больше не действует**. Оно дало 1472 строки, шесть слоёв,
четыре самотеста и ни одного успешного вылета. Инъекцию прокси, `RosLink`,
`LEDBackend`, `MissionConfig`/`Pilot` не восстанавливать.

### Что от него осталось

Ровно одно: `import rospy` стоит не в первой строке файла, а **после** разбора
аргументов, чтения карты, печати сводки и проверки связи со станцией. Отсюда
работает `--check`. Правило простое: всё, что не про ROS (карта, аргументы,
UDP, ожидание оператора), пишется **выше** этой границы; новая ROS-зависимость
— ниже.

### Порядок файла

Восемь блоков, в этом порядке: докстринг → импорты stdlib → константы →
функции без ROS → разбор аргументов и сводка → `--check` и выход → импорт ROS
и прокси → линейный сценарий. Новый шаг сценария — это ещё один блок
`# ─── N. …` в линейном коде, а не класс и не функция-обёртка.

### Правила отказов

1. **У каждого ожидания есть срок**, и по его истечении дрон идёт **дальше по
   сценарию, к посадке** — не в возврат, не в повтор, не в бесконечный цикл.
   Молчащая станция не повод висеть над кубом, пока не сядет батарея.
2. **Отказ вспомогательной подсистемы** (лента, станция, арминг) печатается и
   не прерывает полёт: дрон в воздухе надо посадить, а не бросить.
3. **Потеря позиции полёт не прерывает.** Прерывание пробовали в удалённой
   версии — оно давало посадки посреди исправного полёта.

### Навигация

Все перелёты — `frame_id='aruco_map'`, абсолютные координаты карты. Взлёт —
единственное исключение, `frame_id='body'` («вверх оттуда, где стою»), потому
что на земле дрон закрывает стартовую метку собой.

`frame_id='aruco_N'` **не использовать**: фрейм метки живёт только пока она в
кадре, а метки станции и старта закрыты кубом и площадкой «Н» физически.

### Протокол станции заморожен

Формат датаграмм совместим с `lib/station_link.py` из ветки
`charging-station` — там полная реализация того же протокола на стороне
станции. Ключи `v/kind/from/to/seq/sid/data`, порт 5801, имена узлов `uav1` и
`station1` в одностороннем порядке менять нельзя: станция перестанет понимать
борт. Сам `station_link.py` в эту ветку не втягивать — там 700 строк с
абстрактным транспортом, борту хватает семидесяти.

## Важные допущения, требующие проверки на площадке

Отмечены в README.md как непроверенные — если меняешь код рядом с ними, не
удаляй пометки, пока допущение не подтверждено:

- **Поворот меток `rot_z = -1.5708`** в `config/field_map.txt` выведен из
  описания «повёрнуты на 90° вправо», а не измерен. Знак проверяется на борту
  по `/aruco_map/pose`; не сошлось — `1.5708`.
- **Посадка на куб 80 см обычным `land()`** — прежняя версия делала спуск по
  `/rangefinder/range`; поведение штатного `land()` на приподнятой поверхности
  документацией Skyris не описано.
- **Имя сервиса `mavros/cmd/arming`** — стандартное для MAVROS, но явно
  документацией Skyris не подтверждено. Нужно только для дизарма.
- **Моторы на станции глушит автодизарм PX4** после `land()`. Доклад `landed`
  утверждает, что они выключены; если на площадке крутятся — добавить
  `disarm()` и туда.
- **Порт 5801, имена `uav1`/`station1`, IP станции** — на реальном железе не
  проверялись. Изоляция клиентов на роутере ломает связь молча.
- **Сценарий с новыми шагами** (запрос посадки, Enter, дизарм) в воздухе ещё
  не летал. Летала версия без них: взлёт, перелёт по `aruco_map`, зарядка,
  возврат, посадка — 2026-08-02.
- **`docs/PLAN.md` устарел** в части связи со станцией: там сказано, что
  сетевого канала между бортом и станцией нет и потому сигналы идут через цвет
  ленты. Канал есть, связь идёт по UDP.
