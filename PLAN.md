# Энергоэстафета — план работы на 4 дня

Основа: `TASK.md`. Порядок — от критически необходимого (без этого нет базовых
баллов и не собрать сценарий) до дополнительного (полировка, если есть запас

разным людям и делать параллельно, если один раз в начале зафиксировать общие
интерфейсы (Шаг 0).

## Шаг 0 (день 1, первые 30–60 минут, все вместе) — Зафиксировать интерфейсы

Дрон — **Skyris Technic 6S** (PX4 + Orange Pi 5 Pro, **ROS 1/rospy**, пакеты
`technic`/`led_msgs`/`aruco_pose`; сервопривод — вне ROS, через утилиту
`gpio`). Подробности и ссылки на документацию — в `TASK.md`, раздел
«Технические уточнения по дрону». Модули `led_interface.py`,
`gripper_control.py`, `energy_relay_vision.py` в репозитории уже приведены
в соответствие с этим API — использовать их, а не писать заново.

Чтобы люди дальше не блокировали друг друга, договориться и коротко записать:

- Сигнатуру функции управления лентой — уже зафиксирована в
  `led_interface.py`: `set_led(pattern, color)` (паттерны: solid / blink /
  rainbow / half-half), backend — `use_technic_ros1_backend()`.
- Сигнатуру захвата груза — уже зафиксирована в `gripper_control.py`:
  `gripper_close()` / `gripper_open()`, backend —
  `use_technic_gpio_gripper(pin, open_pulse=..., close_pulse=...)`.
- Формат вывода детектора — уже зафиксирован в `energy_relay_vision.py`
  (`StationVision`/`TechnicROS1Vision`): решить, используем ли для ID/позиции
  метки готовый `aruco_pose` (топик `aruco_detect/markers`) или свой
  детектор из этого модуля — рекомендация: `aruco_pose` для ID/позиции,
  свой HSV-детектор только для цвета станции.
- Формат команд между БВС и станцией: запрос посадки, разрешение, сигнал
  «зарядка завершена» (через LED-сервисы `technic`, см. ниже).
- Кто ведёт скрипт БВС-1, кто БВС-2, кто — код зарядной станции.
- `open_pulse`/`close_pulse` для конкретного сервопривода захвата и номер
  `pin` — их нужно подобрать на реальном железе в первый день (см. 1.1/1.2).

Без этого шага дальнейшая параллельная работа не сложится — остальные модули
пишутся «под мок» этих интерфейсов и стыкуются только на Приоритете 5.

## Приоритет 4 — Связь и синхронизация (день 3)

Сшивает отдельные скрипты и станцию в единый сценарий. Каждая задача — в
своём отдельном модуле (не внутри `bvs1_flight.py`/`bvs2_flight.py`), чтобы
проверять логику самотестом изолированно, без реального ROS 1/сети/дрона —
интеграция в полётные скрипты остаётся за Приоритетом 5.

| # | Задача | Статус |
|---|--------|--------|
| 4.1 | Протокол БВС↔станция: запрос посадки, разрешение, «зарядка завершена», ввод команды с клавиатуры для взлёта БВС-1 после зарядки | **Готово**: `station_protocol.py` |
| 4.2 | Синхронный взлёт двух БВС + асинхронное выполнение задач через события/таймеры (не через жёсткие `sleep`, чтобы попытка не разваливалась при задержках) | **Готово**: `mission_sync.py` |

**Готово в 4.1** (`station_protocol.py`): т.к. отдельного сетевого канала
между бортовым компьютером БВС и Raspberry Pi станции нет (см. Шаг 0),
сигналы «запрос посадки»/«разрешение» реализованы через цвет, который видит
камера другой стороны — `Signal.LANDING_REQUEST` (`red`, уже используемый
цвет индикации поиска станции) и `Signal.LANDING_GRANTED` (`green` на
ленте станции), с функциями `send_signal()`/`wait_for_signal()` (опрос без
жёсткого `sleep` на весь тайм-аут — шаг `poll_interval`, таймаут кидает
`SignalTimeout`). Цвет читается через переданную функцию-читатель
(`ColorReader`), не завязанную на `StationVision`/OpenCV напрямую — в бою
это обёртка над `energy_relay_vision.StationVision.detect()`, в самотесте —
заглушка. «Зарядка завершена» для БВС-1 — по TASK.md (алгоритм, шаг 5)
это явно команда с клавиатуры, а не зрение: `wait_for_takeoff_command()`
блокируется до ввода оператора (Enter/`go`, без учёта регистра), при
нераспознанном вводе переспрашивает, а не прерывает миссию по опечатке.
Проверено самотестом (`--self-test`); полевая отладка — `--wait-takeoff-command`.

**Готово в 4.2** (`mission_sync.py`): БВС-1 и БВС-2 — независимые процессы
на разных бортовых компьютерах, синхронизировать взлёт через
`threading.Event` нельзя — нужен канал по сети (в комплекте есть роутер).
`TakeoffBarrier` — координатор-рандеву поверх TCP:
`serve_takeoff_barrier()` (обычно на ноутбуке оператора) ждёт подключения
`party_count` участников и только тогда шлёт сигнал «взлёт» всем сразу;
`wait_at_takeoff_barrier()` — клиентская сторона на каждом БВС, с
переподключением, если координатор ещё не поднят. Самотестом проверено, что
подключившийся первым участник не улетает раньше второго (разница момента
отпуска < 0.15с при заданной задержке подключения 0.3с) и что при неполном
составе координатор никого не отпускает, а таймаутится сам. Для
асинхронного выполнения задач без жёсткого `sleep` — `run_concurrently()`:
запускает несколько задач каждую в своём потоке, собирает `TaskResult` по
каждой (включая исключение, если задача упала, и таймаут, если зависла),
не давая одной задаче заблокировать ожидание другой; полезно для наземной
оркестрации/самотеста сценария сразу двух бортов (например, в Gazebo).
Полевая отладка координатора отдельно от полётных скриптов — `--serve`/
`--wait`.

## Приоритет 6 — Безопасность и анти-штрафы (весь период, отдельный ответственный)

Идёт фоном с первого дня, не блокирует остальных, но должно быть готово
к каждой попытке:

- АКБ > 3.1 В/ячейка, заряд пульта > 40%, целая изоляция проводов.
- Дрон не остаётся вне зоны с подключённым АКБ и установленными пропеллерами.
- Отработана демонстрация KILL SWITCH перед первым тестовым полётом.
- Тайминг ухода из зоны: за 30 сек до конца попытки — на выход.

Штрафы здесь дешевле избежать заранее, чем терять баллы по ходу (см. `TASK.md`).
