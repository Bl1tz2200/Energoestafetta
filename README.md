# Энергоэстафета

## Запуск

```bash
# боевой запуск БВС-1: взлёт -> перелёт к станции по меткам -> посадка на куб
python3 uav1_flight.py --map config/field_map.txt \
    --start-marker 48 --station-marker 5 --station-height 0.8

# проверка зрения на дроне БЕЗ моторов (что видно, где мы, каким будет маршрут)
python3 uav1_flight.py --probe --map config/field_map.txt

# на ноутбуке, без ROS и дрона
python3 lib/marker_nav.py --self-test                  # самотест расчётов
python3 lib/marker_nav.py --map config/field_map.txt   # показать деревья и маршрут
```

Дрон ставится **на стартовую метку**, пульт с KILL SWITCH — у оператора.
Ставьте дрон носом вдоль ряда меток (любой разворот кратно 90°): тогда каждый
перегон — одна команда вместо двух, миссия короче примерно на 20 секунд.

### Шпаргалка: все команды

Всё, что вообще запускается в этом репозитории. Подробности по каждому пункту
— в разделах ниже.

**На ноутбуке, без ROS и дрона**

```bash
python3 lib/marker_nav.py --self-test                  # самотест расчётов
python3 lib/marker_nav.py --map config/field_map.txt   # деревья и маршрут
python3 lib/marker_nav.py --map config/field_map.txt \
    --start-marker 48 --station-marker 5 --tree-clearance 0.8   # маршрут при другом зазоре
python3 lib/led_interface.py --self-test               # самотест LED
python3 uav1_flight.py --help                          # все флаги со значениями
```

**Перенос кода на Orange Pi**

```bash
ssh orangepi@<ip-бвс> 'cd ~/energoestafetta && git pull'          # вариант А
rsync -avz --exclude '__pycache__' --exclude '*.pyc' \
    ./ orangepi@<ip-бвс>:~/energoestafetta/                       # вариант Б
ssh orangepi@<ip-бвс> 'cd ~/energoestafetta && python3 lib/marker_nav.py --self-test'
```

**Отладка: проверка осей и камеры (моторы не включаются)**

```bash
python3 debug_axes.py --map config/field_map.txt      # оси X/Y: дрон носим руками
python3 debug_camera.py --map config/field_map.txt    # метки, масштаб, место по кадру
python3 debug_camera.py --cycles 1                    # один кадр и выход

python3 debug_axes.py --self-test                     # логика диагноза, без ROS
python3 debug_camera.py --self-test                   # расчёты, без ROS и камеры
```

**На борту: окружение и проверка без моторов**

```bash
source /opt/ros/noetic/setup.bash        # только в неинтерактивном контексте:
source ~/technic_ws/devel/setup.bash     # при входе по SSH это делается само

# ГЛАВНАЯ проверка перед полётом: PX4 получает положение от aruco_map?
rostopic hz /mavros/vision_pose/pose     # должно идти ~10-30 Гц, без пауз
rostopic echo -n1 /aruco_map/pose        # координаты = реальному месту дрона
cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt   # сверить с config/field_map.txt

python3 uav1_flight.py --probe --map config/field_map.txt   # зрение, моторы не трогаем
python3 uav1_flight.py --probe --aruco-dict DICT_4X4_100    # если метки не распознаются
chmod +x uav1_flight.py lib/marker_nav.py lib/led_interface.py   # если нужен ./запуск
```

**Полёт**

```bash
# короткий маршрут — первый вылет после любой правки: одна метка от старта.
# Куба там нет, поэтому дрон сядет на пол и напишет «похоже, под дроном пол»:
# проверяется только перелёт, а не посадка на станцию
python3 uav1_flight.py --map config/field_map.txt --station-marker 41

# боевой запуск
python3 uav1_flight.py --map config/field_map.txt \
    --start-marker 48 --station-marker 5 --station-height 0.8

# осторожный: медленнее, мягче доводка, больше попыток
python3 uav1_flight.py --map config/field_map.txt \
    --speed 0.2 --gain 0.5 --hop-pad 1.2 --tries 12

# лог в файл и на экран одновременно
python3 uav1_flight.py --map config/field_map.txt 2>&1 | tee ~/log_uav1.txt
```

`Ctrl+C` в терминале — штатный способ прервать попытку: дрон гасит движение и
садится. KILL SWITCH на пульте остаётся последним средством.

**Разбор проблем**

```bash
# дрон летит рывками, --speed не помогает: дробить перелёт
python3 uav1_flight.py --map config/field_map.txt --micro-step 0.06

# в логе «курс увело на N°»: включить удержание курса
python3 uav1_flight.py --map config/field_map.txt --hold-yaw
python3 uav1_flight.py --map config/field_map.txt --hold-yaw --yaw-sign -1   # если стало хуже

# миссия срывается у станции («над станцией встать не удалось»)
python3 uav1_flight.py --map config/field_map.txt \
    --blind-tolerance 0.25 --blind-confirm 2

# кроны деревьев шире ожидаемого — маршрут в обход
python3 uav1_flight.py --map config/field_map.txt --tree-clearance 0.8

# запасной режим: навигация по камере вместо aruco_map
python3 uav1_flight.py --map config/field_map.txt --nav-mode markers

# другая раскладка поля (метки объявляют перед попыткой)
python3 uav1_flight.py --map config/field_map.txt \
    --start-marker 42 --station-marker 37 \
    --blind-markers 0,5,37,42 \
    --tree-markers 12,13,19,20 --tree-markers 9,10,16,17
```

## Предполётная проверка координат (10 минут на поле)

Порядок, который нужно пройти **до первого взлёта** и повторить после любой
смены раскладки поля или перезаливки образа. Ни один шаг не включает моторы;
для переноски дрона руками пропеллеры лучше снять.

Каждый шаг отвечает на один вопрос и имеет однозначный признак «сошлось».
Не сошлось — чинить здесь же, дальше не идти: следующий шаг всё равно
покажет мусор.

### Шаг 1. Раскладка объявлена — вписать её в аргументы

Организаторы называют метки старта, станции, груза и деревьев. Всё это —
аргументы, а не константы. Собрать свою строку запуска и дальше использовать
только её:

```bash
python3 lib/marker_nav.py --map config/field_map.txt     --start-marker 48 --station-marker 5
```

**Сошлось:** напечатан маршрут (например `41 -> 34 -> 27 -> 20 -> 13 -> 6 -> 5`)
и координаты деревьев. Глазами проверить, что маршрут идёт туда, куда нужно,
и обходит деревья.

**Не сошлось:** «Маршрут A -> B не строится» — цель окружена деревьями при
текущем `--tree-clearance`, уменьшить его или проверить `--tree-markers`.

### Шаг 2. Карта на платформе — та же, что у нас

Это самая частая причина всех бед: наш скрипт и PX4 берут позицию из ноды
`aruco_map`, а она читает **свой** файл.

```bash
cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt
diff <(grep -v '^#' config/field_map.txt)      <(grep -v '^#' ~/technic_ws/src/technic/aruco_pose/map/map1.txt) && echo СОВПАДАЮТ
```

**Сошлось:** `diff` молчит, напечатано `СОВПАДАЮТ`.

**Не сошлось:**

```bash
cp config/field_map.txt ~/technic_ws/src/technic/aruco_pose/map/map1.txt
rosnode kill /aruco_map    # respawn="true" поднимет ноду заново
```

### Шаг 3. Нода жива и позиция уходит в PX4

```bash
rosnode list | grep aruco                # должны быть aruco_detect и aruco_map
rostopic hz /mavros/vision_pose/pose     # Ctrl+C через пару секунд
```

**Сошлось:** обе ноды в списке, частота ~10–30 Гц без пауз.

**Не сошлось:** нода не поднята или `aruco_vpe` выключен в `aruco.launch` — у
PX4 нет источника положения, и дрон не удержит точку **ни в каком** режиме.

### Шаг 4. Камера видит метки и не врёт в масштабе

Держа дрон на вытянутых руках над полем (метр-полтора), один кадр:

```bash
python3 debug_camera.py --map config/field_map.txt --cycles 1
```

**Сошлось:** видны ID, которые физически под дроном; строка
`шаг решётки: замер 1.00 м, по карте 1.00 м`; расхождение с `aruco_map`
меньше 0.3 м.

**Не сошлось:**

| Что видно | Причина | Что делать |
| --- | --- | --- |
| `меток в кадре нет` | не тот словарь, грязная линза, расфокус | `--aruco-dict DICT_4X4_100`, протереть и навести резкость |
| `ЧУЖИЕ ID` | в кадре чужая разметка или не тот словарь | сверить словарь с организаторами |
| `РАЗМЕР МЕТКИ не тот в N раза` | неверен `--marker-size` или сама метка другого размера | померить метку рулеткой |
| `РАСХОДЯТСЯ` с `aruco_map` | на платформе другая карта | вернуться к шагу 2 |

### Шаг 5. Оси X и Y совпадают с полем — главный шаг

```bash
python3 debug_axes.py --map config/field_map.txt
```

Скрипт проводит по трём меткам, в каждой ждёт Enter и усредняет замеры:

| Ставим дрон на | Ожидаем |
| --- | --- |
| 48 (начало координат) | (0.00, 0.00) |
| 41 (ось X) | (1.00, 0.00) — вырос **x** |
| 47 (ось Y) | (0.00, 1.00) — вырос **y** |

**Сошлось:** `ОСИ СОВПАДАЮТ: карта на платформе соответствует полю`.

**Не сошлось:** диагноз печатается словами — «ЗЕРКАЛЬНАЯ карта», «X и Y
ПЕРЕПУТАНЫ МЕСТАМИ», «ось X направлена В ОБРАТНУЮ сторону», «карта ПОВЁРНУТА
на N°». Все эти случаи лечатся шагом 2; если после замены карты диагноз тот
же — поле физически развёрнуто относительно нумерации, и надо менять
`config/field_map.txt`, а не платформу.

Отдельно: если скрипт пишет `позиция скачет на N м`, оси сравнивать рано —
сначала освещение, фокус и калибровка (шаг 4).

### Шаг 6. Камера видит поле с рабочей высоты

`--probe` — **стационарная** проверка: дрон не взлетает и никуда не летит, он
только смотрит и печатает. Ставить его надо **рядом** с метками или держать
над полем руками; метку прямо под собой он не видит никогда — она либо
закрыта объектом, либо просто не влезает в кадр.

```bash
python3 uav1_flight.py --probe --map config/field_map.txt
```

**Сошлось:** видны ID тех меток, что физически в кадре; `aruco_map` отдаёт
позицию, похожую на правду; печатается маршрут.

**Не сошлось:** `aruco_map: позиции нет` — вернуться к шагам 2–3; меток не
видно вовсе — к шагу 4.

Полезно заодно замерить, **с какой высоты видно две метки**: поднимайте дрон
руками и смотрите строку `метки:` в `debug_camera.py`. На этом поле пара
появляется примерно с 2 м — от этого зависит, работоспособен ли запасной
режим `markers` (ему нужны две), и потому `--alt` стоит 2.0.

### Шаг 7. Первый вылет — короткий

Только теперь. Одна метка от старта, площадка расчищена, пульт с KILL SWITCH
у оператора:

```bash
python3 uav1_flight.py --map config/field_map.txt --station-marker 41 2>&1 | tee ~/log1.txt
```

**Сошлось:** в логе `ПОСЛЕ ВЗЛЁТА по aruco_map` с расхождением меньше 0.7 м,
затем `над меткой 41`. Куба на 41 нет, поэтому дрон сядет на пол и напишет
`похоже, под дроном пол` — это ожидаемо, проверялся только перелёт.

**Уехал на взлёте:** `УЕХАЛ на N м при взлёте — возвращаемся на старт` — это не
срыв. Место известно точно, команда идёт абсолютной точкой карты, поэтому дрон
сначала возвращается на стартовую метку и только там сверяется (строгость
`--start-tolerance` не меняется — меняется момент проверки). Не вернулся или не
удержался — вот это уже VPE, и лететь нельзя.

**Не сошлось:** `дрон не удержал точку` — вернуться к шагу 3, дело в VPE, а не
в скрипте. Что именно случилось, показывают строки `взлёт t=…с:`, которые
сценарий печатает раз в `--watch-period` (0.5 с) прямо во время набора высоты:

| Что в строках `взлёт t=…с` | Что это значит | Куда смотреть |
| --- | --- | --- |
| `позиции нет`, потом сразу большое место | PX4 держал точку вслепую, пока карта не попала в кадр, и за эти секунды его снесло | взлетать ниже (`--alt 1.2`), проверить, есть ли у PX4 второй источник (оптический поток); ставить дрон так, чтобы соседние метки были видны раньше |
| место растёт ровно и без разрывов | дрон действительно уезжает при живой позиции — положительная обратная связь по курсу VPE | сверить курс `/mavros/vision_pose/pose` с реальным, `debug_axes.py` |
| место скачком меняется на метр-полтора | дрон стоит, врёт карта на платформе | `map1.txt` против `config/field_map.txt` (шаг 2) |

После этого можно запускать полный маршрут.

### Все флаги `uav1_flight.py`

#### Поле и цели

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--map` | `config/field_map.txt` | карта поля (`id size x y z rot_z rot_y rot_x`) |
| `--start-marker` | `48` | метка, с которой взлетаем; после взлёта расчётное место сверяется с её координатами |
| `--start-recover` | `2.0` | докуда уехавшего при взлёте дрона возвращать на старт по карте перед сверкой, м (`0` — не возвращать, прерывать сразу). Только режим `aruco-map` |
| `--station-marker` | `5` | метка зарядной станции (закрыта кубом, доводка по карте) |
| `--station-height` | `0.8` | высота куба станции, м |
| `--blind-markers` | `0,5,37,48` | метки, физически закрытые объектами (площадка «Н», кубы станций, груз) — камера их не видит никогда; `none` — таких нет |
| `--start-tolerance` | `0.7` | допуск сверки места со стартовой меткой после взлёта, м |
| `--nav-mode` | `aruco-map` | `aruco-map` — место берётся у платформы, `navigate()` абсолютными точками карты (так летают соперники); `markers` — считается по кадру камеры |
| `--map-tolerance` | `0.25` | «дошли до узла» в режиме `aruco-map`, м |
| `--search-radius` | `0.4` | плечо креста при поиске потерянной позиции, м |
| `--search-rounds` | `2` | сколько раз обойти зону крестом, прежде чем сдаться |
| `--blind-tolerance` | `0.15` | какой расчётный остаток считать «встали» над закрытой меткой, м — **поднимать, если миссия срывается у станции** |
| `--blind-confirm` | `3` | столько кадров подряд остаток должен быть мал |

#### Высота и скорости

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--alt` | `2.0` | рабочая высота, м (должна быть выше деревьев на `--tree-vertical-margin`) |
| `--speed` | `0.3` | скорость перелёта, м/с |
| `--climb-speed` | `1.5` | скорость набора высоты, м/с. Больше горизонтальной намеренно: до высоты захвата карты PX4 летит вслепую, а дрейф там растёт как `t²` — важна короткость взлёта, а не мягкость |
| `--descent-speed` | `0.2` | скорость на спуске к кубу, м/с |
| `--alt-fix` | `0.3` | предел поправки высоты за одну команду, м |
| `--micro-step` | `0` | смягчение: дробить перелёт на команды по столько метров. `0` — одной командой, как в `fly_head`; `0.06` — мягко, **если дрон летит рывками** |
| `--micro-pause` | `0.3` | пауза между дроблёными командами, с; вместе с `--micro-step` задаёт фактическую скорость (0.06/0.3 = 0.2 м/с) |
| `--step-length` | `0.3` | максимум дистанции на один замер по меткам, м — **ограничивает увод курса за перелёт** |
| `--hold-yaw` | выкл. | доворачивать курс к снятому после взлёта; по умолчанию курс только измеряется и печатается в лог |
| `--yaw-sign` | `1` | `-1`, если с `--hold-yaw` дрон закручивается сильнее (знак команды yaw на этой сборке не проверен) |

#### Зрение и наведение

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--marker-size` | `0.33` | сторона метки, м — по ней считается масштаб кадра и высота |
| `--aruco-dict` | `DICT_4X4_50` | словарь ArUco; если `--probe` не видит меток — начинать отсюда |
| `--gain` | `0.7` | какую долю промаха отрабатывать за раз (больше — быстрее, но проскок) |
| `--tol` | `0.08` | «над меткой»: доля диагонали кадра (растёт с высотой, ≈0.25 м на 2 м) |
| `--tries` | `8` | сколько кадров на один узел, дальше узел пропускается |
| `--hop-pad` | `0.8` | запас к паузе перелёта на разгон, торможение и успокоение, с |
| `--hop-max-steps` | `1.5` | предел одной команды в шагах решётки |
| `--watch-period` | `0.5` | как часто печатать место по `aruco_map`, пока дрон отрабатывает команду; `0` — не печатать |

#### Деревья и границы

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--tree-markers` | четыре группы: `12,13,19,20`, `38,39,45,46`, `9,10,16,17`, `28,29,35,36` | метки, в общем углу которых стоит дерево; флаг **повторяемый**, `--tree-markers none` — деревьев нет |
| `--tree-height` | `1.0` | высота дерева, м |
| `--tree-clearance` | `0.5` | зазор до ствола **при построении маршрута**, м. `0.5` — проход вплотную вдоль дерева (маршрут короче на 2 перегона), `0.8` — в обход, на ячейку в сторону |
| `--tree-guard-clearance` | `0.3` | зазор **сторожа**: ближе этого к стволу лететь нельзя, команда отменяется и миссия прерывается. Должен быть меньше `--tree-clearance` (проверяется до взлёта) |
| `--tree-vertical-margin` | `0.4` | на сколько `--alt` обязана превышать `--tree-height`, иначе отказ до взлёта |
| `--geofence-margin` | `0.5` | запас геозоны за крайними метками поля, м |

#### Посадка на куб

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--descent-step` | `0.15` | шаг спуска, м |
| `--touchdown-range` | `0.15` | дальномер ближе этого — считаем, что стоим, и дизармим |

#### ROS и режимы

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--camera-topic` | `main_camera/image_raw` | топик кадра |
| `--rangefinder-topic` | `/rangefinder/range` | топик дальномера |
| `--probe` | выкл. | проверка зрения без моторов, миссия не выполняется |
| `--quiet` | выкл. | не печатать ход миссии |

Остальные пороги (успокоение, слепой подъём, подтверждение доводки на закрытую
метку, лимит отказов `navigate`) флагов не имеют — они в `MissionConfig` в
начале `uav1_flight.py`.

### Флаги `debug_axes.py` — проверка осей

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--map` | `config/field_map.txt` | карта поля, по ней считаются ожидаемые координаты |
| `--markers` | `41,34,40` | **вот этот задаёт три метки**: «начало, метка по оси X, метка по оси Y» |
| `--samples` | `10` | сколько замеров усреднить в каждой точке |
| `--pause` | `0.2` | пауза между замерами, с |
| `--self-test` | выкл. | проверить логику диагноза без ROS и дрона |

**Как выбрать свою тройку.** Нужны три метки, у которых по карте вторая на
1 м по **X** от первой, а третья — на 1 м по **Y**, и ни одна не закрыта
объектом (не из `--blind-markers`). Готовые варианты:

```bash
python3 debug_axes.py --markers 41,34,40   # у старта (по умолчанию)
python3 debug_axes.py --markers 27,20,26   # ближний край поля
python3 debug_axes.py --markers 24,17,23   # центр поля
```

Проверять «на глаз» не нужно: скрипт сам печатает ожидаемые координаты в
подсказке — `держите дрон над меткой 34 (ожидаем 2.00, 0.00)`. Если там не то,
что вы ожидали от этой метки, тройка выбрана неудачно.

Метку, закрытую объектом (48 — площадка «Н», 5 и 37 — кубы станций, 0 — груз),
в тройку брать **нельзя**: над ней платформа не даст позиции.

### Флаги `debug_camera.py` — проверка камеры и масштаба

| Флаг | По умолчанию | Зачем |
| --- | --- | --- |
| `--map` | `config/field_map.txt` | карта поля, с ней сверяется замеренный шаг решётки |
| `--marker-size` | `0.33` | сторона метки, м — по ней считается масштаб кадра |
| `--aruco-dict` | `DICT_4X4_50` | словарь ArUco; если метки не распознаются — начинать отсюда |
| `--camera-topic` | `main_camera/image_raw` | топик кадра |
| `--frame-timeout` | `2.0` | сколько ждать кадр, с |
| `--cycles` | `0` | сколько кадров разобрать (`0` — до `Ctrl+C`) |
| `--pause` | `1.0` | пауза между кадрами, с |
| `--self-test` | выкл. | проверить расчёты без ROS, камеры и OpenCV |

Этим же скриптом меряется, **с какой высоты видно две метки**: поднимайте дрон
руками и смотрите строку `видно меток:`. Для запасного режима `markers` это
критично — ему нужны две.

## Файлы

- `lib/led_interface.py` — управление светодиодной лентой БВС-1 (`set_led`,
  паттерны Табл.1). К полётному сценарию пока не подключён — индикация
  ставится следующим шагом.

## БВС-1 по видимым меткам: `uav1_flight.py`

Полёт БВС-1 к своей зарядной станции. Задача этого этапа — **взлететь,
долететь до станции и сесть на куб**; зарядка, индикация, возврат и связь со
станцией сюда ещё не входят.

Чем отличается от прежнего решения (`bvs1_flight.py`, удалено):

| | было | стало (`uav1_flight.py`) |
| --- | --- | --- |
| Позиция | `get_telemetry(frame_id='aruco_map')` — глобальная локализация платформы | только кадр `main_camera/image_raw` + свой `cv2.aruco`; телеметрия не используется вообще |
| Высота | `z` в кадре карты | сторона метки в пикселях (эталон снимается после взлёта) |
| Курс | удержание `yaw=NaN` | не удерживается: поворот поля меряется по кадру заново каждый раз |
| Команда | `navigate()` в `aruco_map`, точка целиком | `navigate()` в `body` смещением от текущего места |
| Маршрут | прямая к цели короткими перегонами | по решётке меток BFS **в обход деревьев** |
| Посадка на куб | спуск по дальномеру + дизарм | так же |

**Почему отказались от `aruco_map`.** 2026-08-01 БВС-1 взлетел, пошёл «по
меткам» в сторону станции, но фактическая траектория увела его за пределы
поля, и он упал: маршрут строился от метки-якоря, ошибка в его выборе
разворачивала весь маршрут, а достоверность позиции никто не проверял —
`aruco_map` уверенно отдавал позицию с другого конца поля. Здесь этой
цепочки нет вовсе: дрон наводится на метку, которую видит прямо сейчас, а
глобальная позиция используется только как сторож (геозона и деревья).

Подход перенесён из проверенного в полёте `fly_head.py` (репозиторий
`Bl1tz2200/Snake`): там точно так же всё считается по метке в кадре, а не по
телеметрии. Полное описание формул — в докстринге `lib/marker_nav.py`.

### Как устроено перемещение

Один в один как в проверенном в полёте `fly_head.py` (репозиторий
`Bl1tz2200/Snake`), функция `Pilot.fly`:

```python
navigate(x=forward, y=left, z=up, yaw=0.0, speed=SPEED, frame_id="body")
time.sleep(hypot(distance, up) / SPEED + HOP_PAD)
```

- **все координаты уходят одной командой** — смещение вперёд/влево и поправка
  высоты вместе, отдельной команды на высоту не появляется;
- `yaw=0.0` в кадре `body` означает «не менять курс» — курс дрона не
  удерживается и не задаётся, навигации он не мешает (камера смотрит вниз, а
  поворот поля меряется по кадру заново);
- смещение задаётся **от текущего места дрона**, поэтому каждая команда
  самодостаточна и не зависит от того, куда его снесло раньше;
- сервис асинхронный, дождаться его можно только паузой: время в пути плюс
  `--hop-pad` на разгон, торможение и успокоение. Снимок с ещё летящего дрона
  даёт промах и раскачку;
- перелёт длиннее `--hop-max-steps` шагов решётки урезается **пропорционально**
  (направление сохраняется): такая длина почти всегда означает неверно
  опознанную опорную метку, и лететь по ней целиком опасно;
- `--gain` 0.7 применяется к промаху **по кадру**: не отрабатываем его разом,
  иначе дрон проскакивает цель. Вектор, посчитанный по карте между метками,
  идёт целиком — он известен точно.

Миссия занимает ~1–1.5 минуты.

**Если дрон летит рывками**, а `--speed` на это не влияет — значит сборка не
отрабатывает аргумент `speed` и воспринимает команду как мгновенный скачок
цели. Тогда включается смягчение `--micro-step 0.06`: та же дистанция уходит
лесенкой команд по 6 см каждые `--micro-pause`, цель всё время держится
рядом с дроном, а фактическая скорость получается 0.2 м/с независимо от того,
как сборка понимает `speed`. Платой идёт время: миссия растягивается до ~3
минут. Порядок подбора: `--speed 0.2` → `--gain 0.5` → `--hop-pad 1.2` →
`--micro-step 0.06`.

Но сначала стоит убедиться, что дело вообще в командах: если дрон не держит
точку **в ручном Position-режиме со сброшенными стиками**, никакие флаги не
помогут — это оценка положения в PX4, а не наши команды.

### Дрон уводит в стену, и его «чуть крутит» по курсу

Это одна беда, а не две. Команда задаётся в осях **корпуса**
(`frame_id='body'`), а направление к цели считается по кадру в осях **поля**.
Пока дрон не крутится, это одно и то же. Но если за время перелёта корпус
подвернул на 10–15°, вектор уезжает вместе с ним — и чем длиннее перелёт, тем
дальше дрон уходит от посчитанного направления. Отсюда и «влетает в стену»
при живом, аккуратном полёте.

Что сделано:

- **Курс измеряется всегда** и печатается в лог, как только увод больше 5°:
  `курс увело на +12°`. Это первое, на что смотреть после полёта.
- **Дистанция на один замер ограничена** `--step-length` (0.3 м): остаток
  пересчитывается по свежему кадру, уже с новым курсом, поэтому увод не
  успевает накопиться в промах.
- **Удержание курса** — флаг `--hold-yaw`: доворот к курсу, снятому после
  взлёта, едет той же командой, что и смещение. По умолчанию выключено, потому
  что знак команды `yaw` на этой сборке не проверен. Если с `--hold-yaw` дрон
  начнёт закручиваться быстрее — знак противоположный, `--yaw-sign -1`.

Почему дрон вообще подворачивает: команд по курсу мы не отдаём, а `yaw=0` в
кадре `body` означает «оставить как есть» — то есть каждая команда принимает
текущий (уже уведённый) курс за норму и увод накапливается. У соперников
этого не видно, если их код держит абсолютный курс в кадре карты.

### Если дрон вялый и не долетает до меток

Сначала смотрим, какая строка в логе, и только потом крутим:

| Строка в логе | Что это | Что крутить, по порядку |
| --- | --- | --- |
| `узел N пропущен` | до узла не довели за `--tries` кадров | `--tries 12` → `--hop-pad 1.2` (дрон успевает долететь до следующего снимка) |
| `над станцией встать не удалось` | не удержался в `--blind-tolerance` нужное число кадров | `--blind-tolerance 0.25` → `--blind-confirm 2` |
| `место` в логе скачет на неподвижном дроне | проблема не в полёте, а в зрении | освещение, фокус, `--marker-size`, `--aruco-dict` |
| `перелёт N м урезан` на каждом кадре | опорная метка опознаётся неверно либо карта не та | сверить `--map` с полем, проверить `--blind-markers` |

**Прошивку не перепрошиваем и на её функции не рассчитываем.** Сборка
экспериментальная, часть функций может отсутствовать, поэтому код не
полагается ни на то, что сервис честно отработает аргумент `speed`, ни на то,
что все сервисы вообще есть: плавность обеспечивается темпом команд со стороны
скрипта, а выключение моторов на кубе, если `mavros/cmd/arming` окажется
недоступен, дожимается штатной посадкой `land()`.

**Параметры PX4 менять не требуется.** Образ платформы приезжает уже
настроенным на полёт в помещении: VPE от `aruco_map`, фьюжн в EKF2/LPE,
пределы скоростей. Команды, летающие по `aruco_map` со стоковыми настройками,
— лучшее доказательство, что крутить там нечего.

Поэтому, если дрон ведёт себя не так, правильный ход — **не подбирать
параметры, а найти отличие от рабочего дрона**. Снять с обоих
**Parameters → Tools → Save to file…** и сравнить файлы: совпали — дело не в
параметрах, разошлись — видно ровно то, что нужно вернуть. Заодно это
страховка перед любой правкой.

Порядок поиска отличий (всё только чтение, ничего не меняем):

```bash
cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt   # карта совпадает с полем?
grep -n aruco_vpe ~/technic_ws/src/technic/launch/aruco.launch   # VPE включён?
rosnode list | grep aruco                              # нода вообще поднята?
rostopic hz /mavros/vision_pose/pose                   # позиция уходит в PX4?
rostopic echo -n1 /main_camera/camera_info             # камера откалибрована?
```

Первая строка — самая частая причина: у нас карта была зеркальной, и это
объясняло всё поведение целиком.

### Что делает дрон, когда позиция потеряна

По документации Clover телеметрия в кадре карты отдаёт **NaN**, если карта не
распознавалась 0.5 с. То есть «места не знаю» — штатная ситуация, а не отказ:
метки уходят из кадра на кочке, при бликах, над кубом. Порядок действий от
безобидного к рискованному (общий для обоих режимов):

1. **Ждём на месте** `--search-wait` (2 с): карта часто возвращается сама.
2. **Поднимаемся** шагами по 0.3 м, пока не наберём +1 м над рабочей высотой —
   обзор шире, в кадр попадает больше меток.
3. **Обходим маленькую зону крестом**: вперёд `--search-radius` (0.4 м) и
   сразу назад, влево и сразу вправо, `--search-rounds` (2) раза. Крест выбран
   не для красоты: каждое плечо компенсируется обратным, поэтому дрон не
   уползает от точки потери — а именно там, по последним достоверным данным,
   он и находится внутри разрешённой зоны.
4. Не нашлось — **стоп и посадка** с сообщением, что проверять: ноду
   `aruco_map`, карту `map1.txt`, освещение.

На земле карта не видна почти всегда — дрон стоит **на** стартовой метке и
закрывает её, а с 10 см камера охватывает пятачок под собой. Это норма:
сценарий пишет «на земле карта не видна — сверимся после взлёта» и проверяет
место уже в воздухе.

### Система координат карты и как проверить оси

Начало — **метка 48** (площадка «Н» БВС-1), ось **X — в сторону метки 41**,
ось **Y — в сторону метки 47**, Z вверх. ROS работает в ENU, тройка правая;
преобразование в NED полётного контроллера делает MAVROS, нам его касаться не
нужно. Координаты меток в `config/field_map.txt` заданы именно так: 48 —
(0.00, 0.00), 41 — (1.00, 0.00), 47 — (0.00, 1.00), станция 5 — (6.00, 1.00).

**Прежняя карта была зеркальной** и это ровно то, из-за чего дрон «путался в
x и y»: в ней 0→6 задавалось как +X, а 0→42 как +Y, хотя физически это
направления «вправо» и «вниз» одного и того же вида сверху. Такую пару осей
никакой поворот с реальностью не совмещает — оценка курса по паре меток
получалась разной для разных пар, а `aruco_map` на платформе решал бы задачу
по геометрии, которой на поле нет. Самотест `marker_nav` теперь проверяет
знак векторного произведения осей и такую карту не пропустит.

**Проверка осей на площадке, без моторов** — отдельный скрипт, две минуты:

```bash
python3 debug_axes.py --map config/field_map.txt
```

Он проводит по трём точкам (48 → 41 → 47), в каждой усредняет десяток замеров
и печатает разброс, а в конце сам ставит диагноз — не приходится сверять
знаки в уме:

```text
--- ИТОГ ---
по карте:  X 48 -> 41 = (+1.00, +0.00), Y 48 -> 47 = (+0.00, +1.00)
по замеру: X = (+0.00, +1.00), Y = (+1.00, +0.00)
  ЗЕРКАЛЬНАЯ карта: оси X и Y образуют тройку противоположного знака
  X и Y ПЕРЕПУТАНЫ МЕСТАМИ
```

Что он ловит: перепутанные оси, обратное направление, поворот карты целиком,
зеркальность и вранье масштаба (замер 1.4 м вместо 1.0 — некалиброванная
камера или неверный `--marker-size`). Разброс больше 0.15 м — позиция скачет,
и сравнивать оси ещё рано.

То же можно посмотреть и в `uav1_flight.py --probe` — он печатает ожидаемые
координаты меток 48, 41 и 47 и позицию от `aruco_map` рядом с оценкой по
камере. Порядок при ручной проверке:

| Дрон над меткой | `aruco_map` должен показать |
| --- | --- |
| 48 | (0.00, 0.00) |
| 41 | (1.00, 0.00) — вырос **x** |
| 47 | (0.00, 1.00) — вырос **y** |

- координаты растут не там, где ожидалось → на платформе старая карта:
  скопировать `config/field_map.txt` в `map1.txt` и перезапустить ноду;
- x и y поменялись местами или растут в минус → карта на платформе
  зеркальная или повёрнута;
- `aruco_map: позиции нет` → нода не поднята, и тогда у PX4 нет источника
  положения вообще (см. «Подготовка окружения на борту»).

### Полёт по `aruco_map` — основной режим

Режим по умолчанию. Место берётся из `get_telemetry(frame_id='aruco_map')`,
цель задаётся абсолютной точкой той же карты —
`navigate(x, y, z, frame_id='aruco_map')`. Так летают соперники. Маршрут,
обход деревьев, геозона и посадка на куб общие со вторым режимом; камера и
`marker_nav` здесь не участвуют вовсе.

Запасной режим — `--nav-mode markers`: место считается по кадру камеры нашим
кодом (см. «Как устроено перемещение»).

**Важное ограничение запасного режима.** Ему нужны **две** метки в кадре: по
одной поворот поля не измерить. На этом поле пара попадает в кадр только
метров с двух, поэтому `--alt` ниже 2.0 в режиме `markers` не работает — дрон
начнёт подниматься «осмотреться» и в итоге откажется лететь. Платформе в
режиме `aruco-map` хватает одной метки, и это ещё один довод в его пользу.

```bash
python3 uav1_flight.py --map config/field_map.txt --nav-mode aruco-map
```

На земле позиция от `aruco_map` **недостоверна и ни на что не влияет**: дрон
стоит на стартовой метке и закрывает её, а камера в десятке сантиметров от
пола видит в лучшем случае кусок соседней метки под острым углом — оценка
уезжает на метр и больше. Сценарий её печатает для сведения и летит дальше;
настоящая сверка идёт после взлёта, с рабочей высоты, и вот она уже жёсткая.

Отличия, о которых стоит знать:

- **курс фиксируется**: `yaw=0` в кадре карты означает «нос вдоль оси X»
  (в сторону метки 41). Дрон один раз доворачивается и дальше держит курс —
  увод, из-за которого команды в `body` уезжали вместе с корпусом, пропадает;
- всё держится на карте платформы: `map1.txt` обязан совпадать с
  `config/field_map.txt`, иначе дрон полетит по несуществующей геометрии.
  Перед взлётом сценарий сам сверяет позицию на земле со стартовой меткой и
  откажется взлетать при расхождении больше `--start-tolerance`;
- закрытые метки (`--blind-markers`) роли не играют: позиция приходит от
  платформы, видеть цель не требуется.

**Закрытые метки.** Часть меток поля камера не увидит никогда: стартовую 48
закрывает площадка «Н», метки станций 5 и 37 — кубы, метку 0 — груз
(`--blind-markers`). Поэтому нигде в коде нет требования «увидеть нужную
метку»:

- над закрытой меткой дрон встаёт **счётом по карте** от соседних видимых, а
  успехом считается малый расчётный остаток, подтверждённый несколькими
  кадрами подряд;
- сверка после взлёта идёт **по координатам**, а не по «вижу ли я метку 48»:
  расчётное место должно сойтись с координатами стартовой метки в пределах
  `--start-tolerance`.

Отсюда же требование к кадру: место определяется по **паре** меток (по одной
поворот поля не измерить). Если в кадре меньше двух, дрон поднимается
осмотреться и только потом продолжает — лететь по «предполагаемому» повороту
он не станет.

**Деревья.** На поле четыре дерева высотой ~1 м, каждое в общем углу четырёх
меток: `12,13,19,20` → (4.5, 0.5), `38,39,45,46` → (0.5, 2.5),
`9,10,16,17` → (4.5, 3.5), `28,29,35,36` → (1.5, 5.5) — координаты в системе
карты (начало в метке 48). Дерево (4.5, 0.5) стоит в 0.25 м от прямой
«старт 48 → станция 5», поэтому маршрут строится по решётке: рёбра ближе
`--tree-clearance` к стволу запрещены.

Зазор до ствола у рёбер решётки принимает всего несколько значений: **0.5 м**
у четырёх рёбер, идущих вплотную вдоль дерева, **0.71 м** у соседних с ними,
дальше — больше. Отсюда смысл флага:

| `--tree-clearance` | Маршрут 48 → 5 | Перегонов | Время миссии |
| --- | --- | --- | --- |
| `0.5` (по умолчанию) | 41 34 27 **20 13 6** 5 | 7 | ~1–1.5 мин |
| `0.8` | 41 34 27 **26 25 18 11 4** 5 | 9 | ~1.5–2 мин |

По умолчанию дрон проходит **вплотную вдоль ствола** (0.5 м по горизонтали от
оси дерева на перегоне 20 → 13) — это два перегона и 7–10 секунд выигрыша.
Держит его при этом не горизонтальный зазор, а высота: 2 м рабочей против
1 м дерева, то есть метр запаса над кроной. Если на площадке кроны окажутся раскидистыми или дрон будет плохо
держать горизонт — ставить `--tree-clearance 0.8` (маршрут уйдёт на ячейку в
сторону) или поднимать `--alt` до 2.0.

Плюс два страховочных слоя, работающих при любом зазоре: рабочая высота
обязана быть выше `--tree-height` на `--tree-vertical-margin` (иначе отказ до
взлёта), а каждый перелёт проверяется целиком — если отрезок пройдёт ближе
`--tree-guard-clearance` к стволу, берётся другая ось или укороченный шаг, а
если безопасного варианта нет — стоп и посадка.

Обратите внимание: у сторожа **свой, меньший** порог
(`--tree-guard-clearance` 0.3 м против планового 0.5 м). Это не небрежность:
команда идёт по осям корпуса, а маршрут проложен по осям поля, поэтому у
развёрнутого дрона фактический перегон всегда немного отходит от идеального
ребра решётки. Если потребовать от сторожа того же зазора, что от
планировщика, он примет эти законные отклонения за опасность и посадит дрон
посреди исправного полёта. Плановый зазор — «как хотим лететь», сторожевой —
«ближе нельзя ни при каких обстоятельствах».

Порядок запуска:

```bash
# 1. Расчётная часть, на ноутбуке, без ROS и дрона
python3 lib/marker_nav.py --self-test
python3 lib/marker_nav.py --map config/field_map.txt   # покажет деревья и маршрут

# 2. На дроне, МОТОРЫ НЕ ВКЛЮЧАЮТСЯ. Дрон стоит рядом с меткой, не на ней
python3 uav1_flight.py --probe --map config/field_map.txt

# 3. Первый полёт: площадка расчищена, пульт с KILL SWITCH у оператора
python3 uav1_flight.py --map config/field_map.txt \
    --start-marker 48 --station-marker 5 --alt 2.0 --speed 0.3

# 4. Боевой запуск — значения по умолчанию
python3 uav1_flight.py --map config/field_map.txt \
    --start-marker 48 --station-marker 5 --station-height 0.8
```

Что должно быть в выводе `--probe`: метки распознаются (значит словарь
`--aruco-dict` верный), сторона метки в пикселях правдоподобна, «шаг решётки»
близок к 1.00 м (иначе неверен `--marker-size`), расчётное место совпадает с
тем, где дрон стоит физически, и напечатанный маршрут обходит деревья.

Что должно быть в выводе полёта:

```text
маршрут 48 -> 5: 41 -> 34 -> 27 -> 20 -> 13 -> 6 -> 5
взлёт на 2.00 м шагами по 1.00 м (frame_id='body')
>>> ВЫСОТА 2.00 м = метка 132 px в кадре (эталон)
>>> ПОСЛЕ ВЗЛЁТА: место (6.02, 5.98), старт 48 в (6.00, 6.00), расхождение 0.03 м | видно: 41 47
>>> ШАГ РЕШЁТКИ: 1.00 м (по карте 1.00 м)
цель 41 | метки: 41 47 | место (6.00, 6.00) | h≈2.00 м
          над меткой 41
...
          над закрытой меткой 5 (остаток 0.09 м, 3/3)
          дальномер 1.20 м при высоте 2.00 м — под дроном куб
          спуск 4: дальномер 0.10 м
>>> БВС-1 НА ЗАРЯДНОЙ СТАНЦИИ, МОТОРЫ ВЫКЛЮЧЕНЫ
```

Если что-то пошло не так:

| Сообщение | Что это значит | Что делать |
| --- | --- | --- |
| `после взлёта не видно ни одной метки` | камера не отдаёт кадр или словарь ArUco не тот | `--probe` на земле, проверить `--aruco-dict` и `cv_bridge` |
| `после взлёта дрон в (...), а стартовая метка 48 — в (...)` | расчётное место не сошлось с координатами стартовой метки | дрон стоит не на той площадке либо карта не та; сверить `--map` с полем |
| `УЕХАЛ на N м при взлёте — возвращаемся` | не срыв: дрона снесло на взлёте, но место известно и он идёт обратно на старт | смотреть, чем кончилось. Повторяется каждый вылет — чинить VPE, а не поднимать `--start-recover` |
| `вернуться на стартовую метку не удалось` | дрон не приходит в заданную точку карты | по маршруту его пускать нельзя: `map1.txt` против поля, курс VPE (`debug_axes.py`) |
| `после возврата дрон в (...)` | пришёл на старт, но там не удержался | дело в VPE: дрон не держит точку в принципе, ослаблять допуски бессмысленно |
| `после взлёта в кадре меньше двух меток` | поворот поля меряется по паре меток, пары нет даже после подъёма | проверить освещение и фокус камеры, убрать посторонние предметы с соседних меток |
| `ПРОВЕРЬТЕ --marker-size` | замер шага решётки разошёлся с картой | померить рулеткой чёрный квадрат метки и вписать в `--marker-size` |
| `узел N пропущен` | до узла не довели за `--tries` кадров | не срыв: миссия идёт к следующему узлу. Повторяется — увеличить `--tries`, затем `--hop-pad` (дрон не успевает долететь до снимка) |
| `над станцией встать не удалось — на куб не садимся` | дрон не удержался в пределах `--blind-tolerance` нужное число кадров | поднять `--blind-tolerance` (0.25) и/или снизить `--blind-confirm` до 2; см. «Если дрон не долетает» |
| `безопасного перелёта нет` | любой ход подводит дрон ближе `--tree-guard-clearance` к стволу или выводит за поле | сажать, разбираться с локализацией; проверить `--tree-markers` под текущую раскладку. Если повторяется на исправном полёте — уменьшить `--tree-guard-clearance` или увеличить `--tree-clearance` |
| `Маршрут A -> B не строится` | цель окружена деревьями при текущем зазоре | уменьшить `--tree-clearance` (печатается в самом сообщении) |
| `navigate отказал 5 раз подряд` | дрон не принимает управление (OFFBOARD/failsafe) | KILL SWITCH/пульт, проверить арм и режим |
| `похоже, под дроном пол, а не куб` | дальномер не увидел ступеньку высотой `--station-height` | дрон встал мимо станции — прервать, проверить `--station-marker` |
| дрон дёргается, резко разгоняется, проскакивает метку | обычно не настройки, а неверная позиция: карта на платформе или калибровка камеры | сверить `map1.txt` с полем и `--probe`; только потом `--speed` вниз → `--gain` 0.5 → `--hop-pad` вверх |

### Подготовка окружения на борту

На борту D1 окружение ROS 1 поднимается само (`/etc/profile.d/ros_env.sh` и
`~/.bashrc` при каждом входе по SSH), вручную ничего делать не нужно.
Команды ниже нужны только в неинтерактивном контексте (systemd-юнит, скрипт
без логин-шелла):

```bash
source /opt/ros/noetic/setup.bash
source ~/technic_ws/devel/setup.bash   # или свой catkin_ws с technic/led_msgs/cv_bridge
```

Платформенный `technic.launch` стартует сам при включении дрона и поднимает
камеру, MAVROS и дальномер.

**Ноду `aruco_map` не выключайте, хотя наш скрипт её не использует.** Метки
`uav1_flight.py` распознаёт сам по кадру и позицию от платформы не берёт —
но её берёт **сам PX4**: `aruco_map` публикует `mavros/vision_pose/pose`, и
без этого у полётного контроллера в помещении нет источника положения. Дрон
тогда не держит точку: раскачивается, подворачивает по курсу и уезжает —
причём ещё до того, как скрипт отдаст хоть одну команду перемещения.

По той же причине карта на стороне платформы должна совпадать с нашей:

```bash
cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt   # сверить с config/field_map.txt

cp ~/energoestafetta/config/field_map.txt ~/technic_ws/src/technic/aruco_pose/map/map1.txt
rosnode kill /aruco_map    # respawn="true" в launch поднимет ноду заново
```

Проверить, что PX4 действительно получает положение (дрон стоит на полу,
моторы выключены):

```bash
rostopic hz /mavros/vision_pose/pose     # должно идти ~10-30 Гц, без пауз
rostopic echo -n1 /aruco_map/pose        # координаты должны совпадать с местом дрона
```

Молчащий или скачущий `vision_pose` — это и есть причина «летит как FPV»;
никакие флаги скрипта этого не лечат.

### Что такое VPE и как его чинить

**VPE — Vision Position Estimate, «положение по камере».** На улице место дрону
даёт GPS. В помещении GPS нет, и его роль играет камера, смотрящая вниз на
метки. Цепочка такая:

```text
камера → aruco_detect → aruco_map → /aruco_map/pose
       → нода aruco_vpe → /mavros/vision_pose/pose
       → MAVROS → MAVLink VISION_POSITION_ESTIMATE
       → EKF2 внутри PX4 → /mavros/local_position/pose
       → контроллер позиции (то, что удерживает точку в OFFBOARD)
```

Наш скрипт стоит **сбоку** от этой цепочки: `navigate()` только говорит «хочу
быть вон там», а *куда именно полетят моторы*, решает PX4 по своей оценке
места. Поэтому если VPE врёт, дрон улетает вперёд ещё до того, как скрипт
отдаст первую команду перемещения, и никакой `--speed`, `--gain` или
`--start-tolerance` этого не изменит.

Порядок проверки — сверху вниз по цепочке, всё **без моторов**, дрон в руках
или на полу:

| # | Что проверяем | Команда | Что должно быть |
| --- | --- | --- | --- |
| 1 | карта на платформе = наше поле | `cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt` | совпадает с `config/field_map.txt` |
| 2 | ноды подняты | `rosnode list \| grep aruco` | есть `aruco_detect` и `aruco_map` |
| 3 | VPE включён в launch | `grep -n aruco_vpe ~/technic_ws/src/technic/launch/aruco.launch` | нода не закомментирована |
| 4 | поток идёт в PX4 | `rostopic hz /mavros/vision_pose/pose` | ~10–30 Гц **без пауз** |
| 5 | место правдоподобно | `rostopic echo -n1 /aruco_map/pose` | совпадает с реальным местом дрона |
| 6 | PX4 принял позицию | `rostopic echo /mavros/local_position/pose` | на неподвижном дроне стоит, не ползёт |
| 7 | оси карты не перепутаны | `python3 debug_axes.py --map config/field_map.txt` | «оси совпадают» (держа дрон над метками 41, 34, 40) |

Шаг 7 — самый важный для вашего случая; `debug_axes.py` для того и написан:
он снимает позицию над тремя метками и сам отличает совпадающие оси от
перепутанных, перевёрнутых, зеркальных и повёрнутых.

#### Если на шаге 6 позиция ползёт на неподвижном дроне

Сначала различить два совершенно разных случая — **видел ли дрон метки во
время замера**:

- **дрон стоял на полу** — метки не видны, VPE нет, и EKF2 остаётся без
  источника положения. Тогда ползущая позиция не поломка, а нормальное
  поведение фильтра без коррекции: он интегрирует акселерометр, а у того
  всегда есть смещение, и двойное интегрирование уводит оценку в одну
  сторону. Это же объясняет снос на первых метрах взлёта;
- **дрон держали над метками**, `rostopic hz /mavros/vision_pose/pose` в
  соседнем терминале показывает ровные 10–30 Гц, а позиция всё равно ползёт —
  вот это поломка: VPE приходит, но EKF2 его не использует.

Проверять надо **одновременно**, в двух терминалах:

```bash
rostopic hz /mavros/vision_pose/pose            # терминал 1: VPE вообще идёт?
rostopic echo /mavros/local_position/pose       # терминал 2: что думает PX4
```

Что смотреть дальше во втором случае:

```bash
rostopic echo -n1 /mavros/imu/data              # в покое ускорение ≈ (0, 0, 9.8)
rostopic hz /mavros/px4flow/raw/optical_flow_rad  # есть ли второй источник — поток
```

Заметное `linear_acceleration.x` в покое (десятые доли м/с²) означает, что
горизонт не откалиброван: фильтр принимает проекцию гравитации за разгон
вперёд. Лечится калибровкой уровня в QGroundControl (**Sensors → Level
Horizon**) — это калибровка, а не подбор параметров, её делать можно. Живой
оптический поток над однородным полом — второй кандидат: он способен выдавать
ложное движение и тянуть оценку за собой.

Курс проверяется отдельно и вручную: поднимите дрон руками на пару метров и
**пронесите на метр вперёд**, глядя на `/mavros/local_position/pose`. Если X
при этом убывает или меняется Y вместо X — контроллер позиции получает ошибку
с неверным знаком и на любое отклонение отвечает **усилением** этого
отклонения. Внешне это ровно то, что видно на площадке: дрон отрывается и
ровно уезжает в одну сторону.

Частота отказов примерно такая: почти всегда виноват шаг 1 (у нас уже была
зеркальная карта — она объясняла всё поведение целиком), потом 4 (дыры в
потоке: метки не в кадре, тусклый свет, расфокус), потом 7.

**Параметры PX4 при этом не трогаем** (см. выше): если все семь шагов сошлись,
а дрон всё равно уезжает — сравнивать надо не значения параметров наугад, а
дамп параметров с рабочего дрона.

#### Отдельный случай: снос на взлёте — это не поломка VPE

На земле дрон закрывает стартовую метку собой, а с 10 см камера видит пятачок
под собой: VPE в этот момент нет **вообще**, и первые метр-полтора подъёма PX4
удерживает точку вслепую, интегрируя смещение акселерометра. Замер на полу это
подтверждает всегда — ползут и X, и Z, — и потому ничего не доказывает: на полу
так и должно быть. Проверять VPE нужно **в воздухе, над метками**.

Ключевое здесь — дрейф вслепую растёт как `½·a·t²`, **квадратично по времени**.
Значит решает не мягкость взлёта, а его короткость:

| `--climb-speed` | Вслепую до 1.5 м | Ожидаемый увод |
| --- | --- | --- |
| `0.3` м/с | 5.0 с | ~1.5 м (замерено 2026-08-01) |
| `0.8` м/с | 1.9 с | ~20 см |
| `1.5` м/с | 1.0 с | ~6 см |

Отсюда умолчание `--climb-speed 1.5` — быстрее горизонтальной скорости,
вопреки первому впечатлению. Мягкий взлёт имел смысл, пока считалось, что дрон
раскачивает наверху; замеры показали другое — его сносит внизу, пока он не
видит карты. Обратная сторона: набор резче, и если дрон клюёт или проскакивает
высоту, `--climb-speed 0.8` — разумный компромисс, увод там всё равно в
пределах `--start-tolerance`.

Остаточный увод добирается возвратом на старт (`--start-recover`), а не
настройками PX4.

### Известная проблема: `SystemError: initialization of cv_bridge_boost raised unreported exception`

Встречается при чтении кадра камеры (`cv_bridge`) на бортах, где рядом с
системным ROS 1 (`/opt/ros/noetic`, OpenCV 4.2 из apt) есть ещё и второй
catkin-workspace `~/ros_lib_ws` с `cv_bridge`, пересобранным под отдельно
установленный `/opt/opencv-4.8` (обычно ради модуля `aruco` для
`technic_ws`). `technic_ws` собран не поверх `ros_lib_ws`, поэтому при
сорсинге `~/technic_ws/devel/setup.bash` catkin пересчитывает
`LD_LIBRARY_PATH` по своей собственной цепочке и в интерактивных
SSH-сессиях непредсказуемо теряет `~/ros_lib_ws/devel/lib` — тогда
официальный `cv_bridge_boost.so` резолвит `libcv_bridge.so` в системную
(apt) версию, которая на некоторых платах падает с этой ошибкой уже при
инициализации (символы совпадают точно — проверено `nm -D`, но сама
связка `libcv_bridge.so`+OpenCV 4.2 оказывается нерабочей в рантайме на
конкретном экземпляре платы; глубже без `gdb` на месте не копали, т.к.
нашлась рабочая альтернатива).

Диагностировано и подтверждено на площадке 2026-07-31 (борт D1): помогает
явно закрепить порядок `LD_LIBRARY_PATH`, а не полагаться на пересчёт
catkin. В конец `~/.bashrc` на затронутом Orange Pi добавлена строка:

```bash
export LD_LIBRARY_PATH=/home/orangepi/ros_lib_ws/devel/lib:$LD_LIBRARY_PATH
```

Этого достаточно для новой сессии, но **любой повторный** `source
.../setup.bash` посреди уже открытой сессии (например, шаг «Подготовить
окружение» выше, если его всё-таки выполнить вручную) заново пересчитывает
`LD_LIBRARY_PATH` и опять роняет `ros_lib_ws/devel/lib` — воспроизведено на
площадке 2026-08-01. Поэтому в `~/.bashrc` там же добавлена самовосстановление
через `PROMPT_COMMAND`, которая проверяет и, если нужно, заново выносит
`ros_lib_ws/devel/lib` на первое место в `LD_LIBRARY_PATH` перед каждым
приглашением командной строки — так что даже случайный ручной пересорс
посреди сессии больше не ломает `cv_bridge`.

Если ошибка появилась на другом борту/после переустановки образа — добавить
обе правки в конец `~/.bashrc` на нём (строку `export LD_LIBRARY_PATH=...`
и функцию `_fix_ld_library_path`/`PROMPT_COMMAND`, см. историю коммитов
README) и **открыть новый терминал/SSH-сессию** (`.bashrc` читается один раз
при старте шелла — уже открытая сессия правку не подхватит; либо выполнить
`source ~/.bashrc` в текущей).

## Проверка без дрона (self-test)

Логика сценария (без rospy/реального полёта) проверяется так:

```bash
python3 lib/marker_nav.py --self-test
python3 lib/led_interface.py --self-test
```

Это не заменяет реальный полёт — только проверяет, что код не сломан
синтаксически/логически (расчёт координат по карте, маршрут в обход
деревьев, высота по метке, LED-паттерны). Расчёт `marker_nav` не требует ни
ROS, ни OpenCV: `cv2` нужен только самому распознаванию меток на дроне.

## Перенос кода на дрон

Разработка идёт на ноутбуке без ROS 1 — самотесты выше это и проверяют. Но
перед выходом на площадку (или перед каждой тестовой/зачётной попыткой, если
код правился между ними) код нужно перенести на Orange Pi БВС-1 и прогнать
самотесты уже там, на актуальном для полёта окружении:

1. **Скопировать файлы на Orange Pi.** Любой вариант, которым уже пользуется
   команда, подходит — репозиторий не привязан к конкретному способу:

   ```bash
   # вариант А — git (если на Orange Pi есть доступ к тому же репозиторию)
   ssh orangepi@<ip-бвс> 'cd ~/energoestafetta && git pull'

   # вариант Б — rsync с ноутбука, без старого __pycache__/незакоммиченного мусора
   rsync -avz --exclude '__pycache__' --exclude '*.pyc' \
       ./ orangepi@<ip-бвс>:~/energoestafetta/
   ```

   Копируется **весь репозиторий целиком** (`lib/`, `config/`, `docs/`
   вместе с корневыми скриптами) — `rsync -avz` рекурсивен по умолчанию,
   отдельно про подкаталоги заботиться не нужно, но если копируете вручную
   (`scp` по одному файлу) — не забудьте `lib/` и `config/`, без них
   скрипт не запустится (`ModuleNotFoundError`/`FileNotFoundError`).

2. **Прогнать самотесты на самом Orange Pi**, а не только на ноутбуке —
   версия Python и установленные пакеты на борту могут отличаться:

   ```bash
   ssh orangepi@<ip-бвс>
   cd ~/energoestafetta
   python3 lib/marker_nav.py --self-test   # и остальные модули, см. выше
   ```

   Если не проходит — почти всегда это версия Python (регламент требует
   3.8) или отсутствующий пакет, а не полётная логика (она уже проверена на
   ноутбуке). Отдельно убедиться, что на борту есть
   `opencv-contrib-python` (модуль `cv2.aruco`) — без него распознавание
   меток не запустится, и это выяснится на следующем шаге.

3. **Проверить зрение уже на Orange Pi** перед реальным запуском (самотесты
   выше камеру не используют) — `--probe` безопасен, моторы не включаются:

   ```bash
   source /opt/ros/noetic/setup.bash
   source ~/technic_ws/devel/setup.bash
   python3 uav1_flight.py --probe --map config/field_map.txt
   ```

4. **Права на исполнение** — большинство скриптов уже отмечены
   исполняемыми (`chmod +x`), но при запуске всегда через `python3 script.py
   ...` (как в этом README) это не обязательно; проверить/восстановить,
   если нужен прямой запуск `./uav1_flight.py`:

   ```bash
   chmod +x uav1_flight.py lib/marker_nav.py lib/led_interface.py
   ```

5. **Если правки делаются прямо в поле** (на Orange Pi, без ноутбука) —
   не забыть скопировать их обратно (`git add`/`commit`/`push` или обратный
   `rsync`), иначе они потеряются при переустановке образа/следующей
   синхронизации с ноутбука.

Итоговый порядок перед каждой попыткой: самотесты на ноутбуке → перенос
**всего дерева** (`lib/`, `config/`, корневые скрипты) на Orange Pi →
самотесты там же → `uav1_flight.py --probe` для проверки камеры и раскладки
поля → реальный запуск.

## Что проверить на площадке в первый день

`uav1_flight.py --probe` (см. выше) закрывает бо́льшую часть этого списка
автоматически и без риска для пропеллеров — начинайте с него, а не с ручной
проверки.

- ~~Направление нумерации `config/field_map.txt` реально совпадает с
  физической раскладкой поля~~ — подтверждено на площадке: метка `0` в
  верхнем левом углу, `6` в верхнем правом, `48` в нижнем правом — совпадает
  с порядком в `config/field_map.txt` (строки сверху вниз, внутри строки
  слева направо).
- Словарь ArUco поля — в коде `DICT_4X4_50` (`--aruco-dict`); если `--probe`
  не видит ни одной метки при исправной камере, дело почти всегда в нём.
- Сторона метки `--marker-size` (0.33 м по регламенту) — по ней считается вся
  геометрия; `--probe` печатает замеренный шаг решётки, он должен быть около
  1.00 м.
- Имя сервиса армирования `mavros/cmd/arming` (стандартное для MAVROS, но не
  подтверждено явно документацией Skyris) — нужно только для дизарма на кубе.
- `--touchdown-range` и `--descent-step` — надо откалибровать по факту на
  кубе 80 см.
- `--tree-clearance` (0.5 м) — радиус крон организаторами не назван, а по
  умолчанию дрон идёт вплотную вдоль ствола (по горизонтали; сверху при
  `--alt` 2.0 остаётся метр запаса). Посмотреть на кроны и при сомнениях
  ставить `0.8` — маршрут длиннее на два перегона.
- `--blind-markers` (`0,5,37,48`) — метки, закрытые площадкой «Н», кубами
  станций и грузом. Сверить со списком, который объявят перед попыткой:
  лишняя метка в списке — потеря точности (дрон не станет наводиться на неё
  визуально, хотя мог бы), недостающая — впустую потраченные попытки на узле.
- `--hop-pad` (0.8 с) — взято с другого дрона: если на каждом шаге дрон
  дёргается, увеличивать именно его.
- `--climb-speed` (1.5 м/с) — расчётное значение, в полёте **не проверено**.
  Оно выведено из того, что дрейф вслепую растёт как `t²`, а не измерено:
  замерен только увод 1.5 м при 0.3 м/с (2026-08-01). Сколько именно останется
  при 1.5 м/с и не начнёт ли дрон клевать на резком наборе — покажет первый же
  вылет по строкам `взлёт t=…с`. Осторожный вариант — `0.8`.
- **Калибровка камеры.** Документация Clover: «Camera calibration can
  significantly improve the quality of nodes related to computer vision: ArUco
  markers detection and optical flow». Формально без неё детектор работает, но
  расстояния считаются через фокусное расстояние: если оно задано неверно в
  1.2 раза, все расстояния и вся позиция `aruco_map` врут ровно в 1.2 раза.

  Ловится это **в `debug_axes.py`**, строкой «МАСШТАБ по оси X/Y»: физически
  дрон переносят на 1 м, а платформа показывает другую величину. Строка «шаг
  решётки» в `debug_camera.py` для этого **не годится** — она считается как
  отношение пикселей (зазор между метками к стороне метки) и от фокусного не
  зависит вовсе. Она ловит другое: неверный `--marker-size` или неверный
  физический размер метки.
- Метки станции и старта (`--station-marker`, `--start-marker`) — раскладку
  объявляют перед попыткой; в коде это аргументы, а не константы. Деревья
  задаются так же — метками (`--tree-markers`), координата ствола считается
  из карты.
- Курс дрона нигде не удерживается и не задаётся: `navigate(frame_id='body')`
  без `yaw` означает «не менять курс», а поворот поля меряется по кадру.
  Никакого `yaw=NaN` (его поддержка на Skyris не подтверждена) в коде больше
  нет.

Подробнее — в `docs/TASK.md` и `docs/PLAN.md`.
