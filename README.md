# Энергоэстафета — БВС-1

Код первого дрона (Skyris Technic 6S, PX4 + Orange Pi 5 Pro, ROS 1/rospy) для
инженерного соревнования «Энергоэстафета», Архипелаг 2026. Задание и регламент —
[docs/TASK.md](docs/TASK.md), план работ — [docs/PLAN.md](docs/PLAN.md).

В репозитории **один полётный скрипт** — `uav1_flight.py`. Он летал на реальном
дроне; предыдущая версия на 1472 строки со слоями, классами и самотестами не
летала ни разу и удалена. Общих модулей (`lib/`) больше нет: всё, что нужно
скрипту, лежит в нём самом, и на борт он возится одним файлом.

## Запуск

```bash
python3 uav1_flight.py --station 192.168.0.21          # боевой запуск
python3 uav1_flight.py                                 # без станции: 5 и 48
python3 uav1_flight.py 5 47 --station 192.168.0.21     # старт не с 48, а с 47
python3 uav1_flight.py --check --station 192.168.0.21  # без моторов и без ROS
python3 uav1_flight.py 12 0 ~/my_field.txt             # своя карта (Gazebo)
```

Позиционные аргументы: **цель**, **точка возврата**, **карта поля**. Флаги
вырезаются до позиционных, поэтому порядок любой. Опечатка в имени флага —
ошибка на земле, а не сюрприз в воздухе.

| Аргумент | Умолчание | Что это |
| --- | --- | --- |
| 1-й | `5` | номер метки зарядной станции |
| 2-й | `48` | номер стартовой метки — это **точка возврата** |
| 3-й | `config/field_map.txt` | карта поля |
| `--station IP` | связи нет | адрес зарядной станции |
| `--check` | — | проверить и выйти, моторы не включать |

Вторая метка на взлёт не влияет: взлёт идёт в `frame_id='body'` — «вверх
оттуда, где стою». Видеть её камерой тоже не нужно, место дрон берёт у ноды
`aruco_map` по любым видимым меткам, а стартовую всё равно закрывает площадка «Н».

До взлёта печатается сводка «старт — цель — путь». **Если точки не те — Ctrl+C,
дрон ещё стоит на земле.** Пульт держать в руках: аварийный переход в ручной
режим — только с него.

## Что делает скрипт

| Шаг | Действие | Лента |
| --- | --- | --- |
| 1 | взлёт на 2 м | жёлтая мигающая |
| 2 | полёт к метке станции | красная |
| 3 | запрос посадки у станции, ожидание разрешения | красная |
| 4 | посадка, зарядка 15 с | красная мигающая |
| — | последние 5 с зарядки | зелёная |
| 5 | ожидание команды оператора (Enter) | зелёная |
| 6 | взлёт, возврат на стартовую метку, посадка | зелёная мигающая |
| 7 | выключение моторов | гаснет |

**Главное правило ожиданий:** у каждого ожидания есть срок, и по его истечении
дрон идёт **дальше по сценарию**, а не зависает. Молчащая станция — не повод
висеть над кубом, пока не сядет батарея; отсутствие оператора — не повод
ночевать на станции. В воздухе дрон ждёт только на шаге 3 и не дольше 20 с.

### Почему координаты карты, а не `frame_id='aruco_5'`

Документация Skyris разрешает лететь прямо к метке
(`navigate(frame_id='aruco_5', x=0, y=0, z=1)`), но фрейм `aruco_N` живёт,
только пока метка видна в кадре. **Метку зарядной станции закрывает куб** — она
не появится в кадре никогда, как и стартовая метка под площадкой «Н». Поэтому
номер переводится в координаты по карте, и дрон летит в `aruco_map`, где место
считается по любым другим видимым меткам.

### Деревья

На поле четыре дерева высотой ~1 м. Планировщика обхода в скрипте **нет** и
флага `--tree-clearance` тоже: рабочая высота 2 м, деревья проходятся сверху по
прямой. Если организаторы поставят что-то выше метра, менять придётся не флаг,
а маршрут.

### Что скрипт делает на отказ

| Что отказало | Когда видно | Что делает скрипт |
| --- | --- | --- |
| `--station` не задан | на земле | летит без станции, разрешения не спрашивает |
| порт 5801 занят | на земле | то же, связь выключена на всю попытку |
| станция молчит на `hello` | на земле | предупреждает и всё равно стартует |
| станция молчит над кубом | в воздухе, ≤20 с | садится без разрешения |
| `landing_denied` | в воздухе | печатает причину, просит до конца срока, садится |
| оператор не нажал Enter | на станции, 60 с | возвращается сам |
| ввод не с терминала | на станции, сразу | возвращается сам, не ждёт |
| нет `mavros/cmd/arming` | в конце | повторный `land()`, балл за дизарм теряется |
| отказ `led/set_effect` | любой шаг | печатает и летит дальше |
| карты меток не видно | любой шаг | печатает «места не знаем», полёт **не** прерывает |

Последняя строка — не недосмотр, а осознанный выбор: скрипт не вмешивается в
траекторию, он её только исполняет и показывает. Прерывать полёт на потере
позиции пробовали в удалённой версии — это давало посадки посреди исправного
полёта.

## Связь с зарядной станцией

Одноранговый UDP: сервера нет, обе стороны слушают **один и тот же порт 5801** и
шлют датаграммы прямо на IP собеседника. Порядок включения не важен, выключенная
станция ничего не вешает — у UDP нет установки соединения.

```json
{"v":1,"kind":"landing_request","from":"uav1","to":"station1","seq":7,"sid":"a3f1c9","data":{}}
```

Обмен за попытку:

```text
БВС-1 на земле
  БВС-1   -> станция   hello             проверка связи, состояние не меняет
БВС-1 завис над кубом
  БВС-1   -> станция   landing_request   повтор раз в 0.5 с, до 20 с
  станция -> БВС-1     landing_granted   садись
        либо           landing_denied    занята/не тот борт, причина в data.reason
  БВС-1   -> станция   landed            сел, моторы выключены
  БВС-1   -> станция   departed          улетел, площадка свободна
```

Каждое сообщение уходит **трижды подряд**: UDP теряет пакеты, а подтверждений в
протоколе нет. Повторы на приёме безвредны — все сообщения идемпотентны.

**Станция опознаёт борт по IP отправителя.** Поэтому мало указать её адрес нам
(`--station 192.168.0.21`) — на её стороне должен быть прописан наш
(`--drone uav1=<IP дрона>`). Датаграмма с чужого адреса отбрасывается молча.

**Имя станции `station1` — константа в коде.** Если станцию поднимут с другим
`--id`, она отбросит наши датаграммы по полю `to`, и внешне это будет выглядеть
как «станция молчит». Меняется в одном месте, рядом с портом.

Формат совместим с `lib/station_link.py` из ветки `charging-station` — это
полная реализация того же протокола, которую использует сама станция. Втягивать
её сюда не нужно: там 700 строк с абстрактным транспортом и дедупом, борту
хватает семидесяти.

Отладка:

```bash
python3 uav1_flight.py --check --station 192.168.0.21   # есть ли связь вообще
tcpdump -n udp port 5801                                # идут ли датаграммы
```

Если `hello` не проходит, а адреса верные — почти всегда виновата **изоляция
клиентов** на роутере: устройства видят интернет, но не видят друг друга.

## Предполётная проверка

### Шаг 0. Скрипт запускается и видит станцию

```bash
python3 -m py_compile uav1_flight.py                    # синтаксис
python3 uav1_flight.py --check --station 192.168.0.21   # карта, сводка, связь
```

Моторы не включаются, ROS не нужен. **Это единственная проверка, возможная не на
дроне** — самотестов в репозитории больше нет.

### Шаг 1. Карта на платформе — та же, что у нас

Это самая частая причина всех бед: наш скрипт и PX4 берут позицию из ноды
`aruco_map`, а она читает **свой** файл.

```bash
diff <(grep -v '^#' config/field_map.txt) <(grep -v '^#' ~/technic_ws/src/technic/aruco_pose/map/map1.txt) && echo СОВПАДАЮТ
```

**Сошлось:** `diff` молчит, напечатано `СОВПАДАЮТ`.

**Не сошлось:**

```bash
cp config/field_map.txt ~/technic_ws/src/technic/aruco_pose/map/map1.txt
rosnode kill /aruco_map    # respawn="true" поднимет ноду заново
```

### Шаг 2. Поворот меток в карте совпадает с полем

В `config/field_map.txt` колонка `rot_z` равна `-1.5708`: метки физически лежат
повёрнутыми на 90° вправо. Квадрат при повороте на 90° накрывает сам себя,
поэтому метка не пропадает и выглядит нормально — сдвигается только нумерация её
углов, и `solvePnP` выдаёт позу, развёрнутую вокруг центра метки. Пока в кадре
одна метка, врёт в основном курс; как только меток несколько, единой позы не
существует вовсе, и оценка скачет при каждой смене набора.

Проверка — поднять дрон руками над известной меткой:

```bash
rostopic echo -n1 /aruco_map/pose     # должно совпасть с реальным местом
```

**Не сошлось** (позиция скачет при смене меток в кадре) — знак противоположный,
менять `-1.5708` на `1.5708` во всех строках и перезапускать `aruco_map`.

### Шаг 3. Нода жива и позиция уходит в PX4

```bash
rosnode list | grep aruco                # должны быть aruco_detect и aruco_map
rostopic hz /mavros/vision_pose/pose     # Ctrl+C через пару секунд
```

**Сошлось:** обе ноды в списке, частота ~10–30 Гц без пауз.

**Не сошлось:** нода не поднята или `aruco_vpe` выключен в `aruco.launch` — у
PX4 нет источника положения, и дрон не удержит точку **ни в каком** режиме.

## Подготовка окружения на борту

На борту D1 окружение ROS 1 поднимается само (`/etc/profile.d/ros_env.sh` и
`~/.bashrc` при каждом входе по SSH), вручную ничего делать не нужно.
Команды ниже нужны только в неинтерактивном контексте (systemd-юнит, скрипт
без логин-шелла):

```bash
source /opt/ros/noetic/setup.bash
source ~/technic_ws/devel/setup.bash   # или свой catkin_ws с technic/led_msgs/cv_bridge
```

Платформенный `technic.launch` стартует сам при включении дрона и поднимает
камеру, MAVROS и дальномер.

**Нода `aruco_map` нужна дважды, и без неё лететь нельзя.** Во-первых, из неё
берёт координаты сам скрипт: все перелёты идут в `frame_id='aruco_map'`.
Во-вторых, её же берёт **PX4** — `aruco_map` публикует
`mavros/vision_pose/pose`, и без этого у полётного контроллера в помещении нет
источника положения. Дрон тогда не держит точку: раскачивается, подворачивает
по курсу и уезжает — причём ещё до того, как скрипт отдаст хоть одну команду
перемещения.

По той же причине карта на стороне платформы должна совпадать с нашей:

```bash
cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt   # сверить с config/field_map.txt

cp ~/energoestafetta/config/field_map.txt ~/technic_ws/src/technic/aruco_pose/map/map1.txt
rosnode kill /aruco_map    # respawn="true" в launch поднимет ноду заново
```

Проверить, что PX4 действительно получает положение (дрон стоит на полу,
моторы выключены):

```bash
rostopic hz /mavros/vision_pose/pose     # должно идти ~10-30 Гц, без пауз
rostopic echo -n1 /aruco_map/pose        # координаты должны совпадать с местом дрона
```

Молчащий или скачущий `vision_pose` — это и есть причина «летит как FPV»;
никакие флаги скрипта этого не лечат.

## Что такое VPE и как его чинить

**VPE — Vision Position Estimate, «положение по камере».** На улице место дрону
даёт GPS. В помещении GPS нет, и его роль играет камера, смотрящая вниз на
метки. Цепочка такая:

```text
камера → aruco_detect → aruco_map → /aruco_map/pose
       → нода aruco_vpe → /mavros/vision_pose/pose
       → MAVROS → MAVLink VISION_POSITION_ESTIMATE
       → EKF2 внутри PX4 → /mavros/local_position/pose
       → контроллер позиции (то, что удерживает точку в OFFBOARD)
```

Наш скрипт стоит **сбоку** от этой цепочки: `navigate()` только говорит «хочу
быть вон там», а *куда именно полетят моторы*, решает PX4 по своей оценке
места. Поэтому если VPE врёт, дрон улетает вперёд ещё до того, как скрипт
отдаст первую команду перемещения, и никакая правка скорости или допусков в
константах этого не изменит.

Порядок проверки — сверху вниз по цепочке, всё **без моторов**, дрон в руках
или на полу:

| # | Что проверяем | Команда | Что должно быть |
| --- | --- | --- | --- |
| 1 | карта на платформе = наше поле | `cat ~/technic_ws/src/technic/aruco_pose/map/map1.txt` | совпадает с `config/field_map.txt` |
| 2 | ноды подняты | `rosnode list \| grep aruco` | есть `aruco_detect` и `aruco_map` |
| 3 | VPE включён в launch | `grep -n aruco_vpe ~/technic_ws/src/technic/launch/aruco.launch` | нода не закомментирована |
| 4 | поток идёт в PX4 | `rostopic hz /mavros/vision_pose/pose` | ~10–30 Гц **без пауз** |
| 5 | место правдоподобно | `rostopic echo -n1 /aruco_map/pose` | совпадает с реальным местом дрона |
| 6 | PX4 принял позицию | `rostopic echo /mavros/local_position/pose` | на неподвижном дроне стоит, не ползёт |
| 7 | оси карты не перепутаны | пронести дрон на метр вперёд, смотреть `/aruco_map/pose` | растёт X, а не Y, и не убывает |

Шаг 7 проверяется руками: поднять дрон над полем, пронести на метр в сторону
метки 41 и смотреть, что в `/aruco_map/pose` растёт именно X. Если меняется Y
вместо X или значение убывает — оси перепутаны или зеркальны, и дрон на любое
отклонение будет отвечать усилением этого отклонения. Раньше это делал
`debug_axes.py`; скрипт удалён вместе с остальными вспомогательными, потому что
проверка занимает полминуты вручную и нужна раз в день.

### Если на шаге 6 позиция ползёт на неподвижном дроне

Сначала различить два совершенно разных случая — **видел ли дрон метки во
время замера**:

- **дрон стоял на полу** — метки не видны, VPE нет, и EKF2 остаётся без
  источника положения. Тогда ползущая позиция не поломка, а нормальное
  поведение фильтра без коррекции: он интегрирует акселерометр, а у того
  всегда есть смещение, и двойное интегрирование уводит оценку в одну
  сторону. Это же объясняет снос на первых метрах взлёта;
- **дрон держали над метками**, `rostopic hz /mavros/vision_pose/pose` в
  соседнем терминале показывает ровные 10–30 Гц, а позиция всё равно ползёт —
  вот это поломка: VPE приходит, но EKF2 его не использует.

Проверять надо **одновременно**, в двух терминалах:

```bash
rostopic hz /mavros/vision_pose/pose            # терминал 1: VPE вообще идёт?
rostopic echo /mavros/local_position/pose       # терминал 2: что думает PX4
```

Что смотреть дальше во втором случае:

```bash
rostopic echo -n1 /mavros/imu/data              # в покое ускорение ≈ (0, 0, 9.8)
rostopic hz /mavros/px4flow/raw/optical_flow_rad  # есть ли второй источник — поток
```

Заметное `linear_acceleration.x` в покое (десятые доли м/с²) означает, что
горизонт не откалиброван: фильтр принимает проекцию гравитации за разгон
вперёд. Лечится калибровкой уровня в QGroundControl (**Sensors → Level
Horizon**) — это калибровка, а не подбор параметров, её делать можно. Живой
оптический поток над однородным полом — второй кандидат: он способен выдавать
ложное движение и тянуть оценку за собой.

Курс проверяется отдельно и вручную: поднимите дрон руками на пару метров и
**пронесите на метр вперёд**, глядя на `/mavros/local_position/pose`. Если X
при этом убывает или меняется Y вместо X — контроллер позиции получает ошибку
с неверным знаком и на любое отклонение отвечает **усилением** этого
отклонения. Внешне это ровно то, что видно на площадке: дрон отрывается и
ровно уезжает в одну сторону.

Частота отказов примерно такая: почти всегда виноват шаг 1 (у нас уже была
зеркальная карта — она объясняла всё поведение целиком), потом 4 (дыры в
потоке: метки не в кадре, тусклый свет, расфокус), потом 7.

**Параметры PX4 при этом не трогаем** (см. выше): если все семь шагов сошлись,
а дрон всё равно уезжает — сравнивать надо не значения параметров наугад, а
дамп параметров с рабочего дрона.

### Отдельный случай: снос на взлёте — это не поломка VPE

На земле дрон закрывает стартовую метку собой, а с 10 см камера видит пятачок
под собой: VPE в этот момент нет **вообще**, и первые метр-полтора подъёма PX4
удерживает точку вслепую, интегрируя смещение акселерометра. Замер на полу это
подтверждает всегда — ползут и X, и Z, — и потому ничего не доказывает: на полу
так и должно быть. Проверять VPE нужно **в воздухе, над метками**.

Ключевое здесь — дрейф вслепую растёт как `½·a·t²`, **квадратично по времени**.
Значит решает не мягкость взлёта, а его короткость:

| Скорость набора | Вслепую до 1.5 м | Ожидаемый увод |
| --- | --- | --- |
| `0.3` м/с | 5.0 с | ~1.5 м (замерено 2026-08-01) |
| `0.8` м/с | 1.9 с | ~20 см |
| `1.5` м/с | 1.0 с | ~6 см |

Мягкий взлёт имел смысл, пока считалось, что дрон раскачивает наверху; замеры
показали другое — его сносит внизу, пока он не видит карты. В скрипте набор
идёт на `CLIMB_SPEED = 1.0` м/с, вдвое быстрее горизонтальной скорости —
вопреки первому впечатлению это и есть защита от сноса. Если дрон клюёт или
проскакивает высоту, константу можно опустить до `0.8`.

## Известная проблема: `SystemError: initialization of cv_bridge_boost raised unreported exception`

Встречается при чтении кадра камеры (`cv_bridge`) на бортах, где рядом с
системным ROS 1 (`/opt/ros/noetic`, OpenCV 4.2 из apt) есть ещё и второй
catkin-workspace `~/ros_lib_ws` с `cv_bridge`, пересобранным под отдельно
установленный `/opt/opencv-4.8` (обычно ради модуля `aruco` для
`technic_ws`). `technic_ws` собран не поверх `ros_lib_ws`, поэтому при
сорсинге `~/technic_ws/devel/setup.bash` catkin пересчитывает
`LD_LIBRARY_PATH` по своей собственной цепочке и в интерактивных
SSH-сессиях непредсказуемо теряет `~/ros_lib_ws/devel/lib` — тогда
официальный `cv_bridge_boost.so` резолвит `libcv_bridge.so` в системную
(apt) версию, которая на некоторых платах падает с этой ошибкой уже при
инициализации (символы совпадают точно — проверено `nm -D`, но сама
связка `libcv_bridge.so`+OpenCV 4.2 оказывается нерабочей в рантайме на
конкретном экземпляре платы; глубже без `gdb` на месте не копали, т.к.
нашлась рабочая альтернатива).

Диагностировано и подтверждено на площадке 2026-07-31 (борт D1): помогает
явно закрепить порядок `LD_LIBRARY_PATH`, а не полагаться на пересчёт
catkin. В конец `~/.bashrc` на затронутом Orange Pi добавлена строка:

```bash
export LD_LIBRARY_PATH=/home/orangepi/ros_lib_ws/devel/lib:$LD_LIBRARY_PATH
```

Этого достаточно для новой сессии, но **любой повторный** `source
.../setup.bash` посреди уже открытой сессии (например, шаг «Подготовить
окружение» выше, если его всё-таки выполнить вручную) заново пересчитывает
`LD_LIBRARY_PATH` и опять роняет `ros_lib_ws/devel/lib` — воспроизведено на
площадке 2026-08-01. Поэтому в `~/.bashrc` там же добавлена самовосстановление
через `PROMPT_COMMAND`, которая проверяет и, если нужно, заново выносит
`ros_lib_ws/devel/lib` на первое место в `LD_LIBRARY_PATH` перед каждым
приглашением командной строки — так что даже случайный ручной пересорс
посреди сессии больше не ломает `cv_bridge`.

Если ошибка появилась на другом борту/после переустановки образа — добавить
обе правки в конец `~/.bashrc` на нём (строку `export LD_LIBRARY_PATH=...`
и функцию `_fix_ld_library_path`/`PROMPT_COMMAND`, см. историю коммитов
README) и **открыть новый терминал/SSH-сессию** (`.bashrc` читается один раз
при старте шелла — уже открытая сессия правку не подхватит; либо выполнить
`source ~/.bashrc` в текущей).


## Перенос кода на дрон

Интернет на борту не нужен и его там нет: `scp` идёт по локальной сети через
Wi-Fi самого дрона. Вариант с `git pull` неприменим по той же причине.

```bash
scp uav1_flight.py orangepi@10.42.0.1:~
scp -r config orangepi@10.42.0.1:~
```

Первое, что делать на борту, — проверить, что файл доехал целым и запускается:

```bash
ssh orangepi@10.42.0.1
python3 -m py_compile uav1_flight.py     # синтаксис, моторы не трогаются
python3 uav1_flight.py --check           # карта и сводка
python3 uav1_flight.py --check --station 192.168.0.21   # плюс связь
```

**Это не формальность.** В среде разработки Python отсутствует, синтаксис на
ноутбуке проверить нечем, самотестов в репозитории не осталось — первая
настоящая проверка кода происходит именно здесь. Только после неё — запуск с
моторами, пульт с KILL SWITCH в руках.

Правки, сделанные в поле прямо на Orange Pi, копировать обратно: следующий `scp`
с ноутбука их затрёт.

## Структура репозитория

```text
uav1_flight.py         единственный полётный скрипт
config/field_map.txt   карта поля 7x7 в формате aruco_pose
docs/TASK.md           задание и регламент
docs/PLAN.md           план работ по приоритетам
CLAUDE.md              инструкции для Claude Code
README.md              этот файл
```

Общих модулей нет и заводить их не нужно. Плоский файл — это решение, а не
недоделка: предыдущая версия с `lib/`, слоями и инъекцией ROS-прокси занимала
1472 строки и не летала.

Карта поля — формат `aruco_pose` (`id size x y z rot_z rot_y rot_x`), нумерация
построчно от левого верхнего угла (метка 0), шаг 1 м, сторона метки 0.33 м.
Начало координат — метка 48, ось X к метке 41, ось Y к метке 47.

## Что проверить на площадке

Раскладка объявляется организаторами перед каждой попыткой — номера меток
задаются аргументами, а не правкой кода.

| Что | Как | Почему важно |
| --- | --- | --- |
| карта платформы = наша | `diff` из «Предполётной проверки» | расхождение = уверенный полёт не туда |
| знак `rot_z` | `/aruco_map/pose` над известной меткой | −1.5708 выведен из описания, а не измерен |
| VPE идёт | `rostopic hz /mavros/vision_pose/pose` | без него дрон не держит точку |
| `mavros/cmd/arming` есть | запуск до конца, строка «МОТОРЫ ВЫКЛЮЧЕНЫ» | иначе теряется балл за автономность |
| `land()` на кубе 80 см | первый же полёт к станции | **не проверено**: прежняя версия делала спуск по дальномеру, эта полагается на штатный `land()` на приподнятой поверхности |
| моторы глохнут на кубе | посмотреть после посадки на станцию | доклад `landed` утверждает, что они выключены; если крутятся — нужен `disarm()` и там |
| UDP 5801 между бортом и станцией | `--check --station <ip>` | изоляция клиентов на роутере ломает связь молча |
| тайминги 15/5 с | по секундомеру | балл за зарядку и индикацию |
| высота 2 м против деревьев 1 м | глазами на первом перелёте | обхода препятствий в скрипте нет |

Отдельно: **сценарий целиком с новыми шагами (запрос посадки, Enter, дизарм) в
воздухе ещё не летал.** Летала версия без них — взлёт, перелёт по `aruco_map`,
зарядка, возврат, посадка.
